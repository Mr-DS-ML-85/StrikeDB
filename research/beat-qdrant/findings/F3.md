# F3: Qdrant Architecture Weaknesses and Limitations

**Research Date:** 2025-07-18
**Purpose:** Identify exploitable weaknesses in Qdrant for competitive positioning

---

## 1. Memory Limitations

### RAM Per Vector Requirements
- **Default behavior:** Qdrant stores ALL vectors in RAM for maximum search performance
- **Memory formula (in-memory mode):** ~`vector_dim × 4 bytes × 1.5` (including index overhead)
  - 768-dim vectors: ~4.6 KB per vector (with HNSW index)
  - 1536-dim vectors: ~9.2 KB per vector (with HNSW index)
  - 100M vectors × 768 dim = **~460 GB RAM** (just vectors + index)
- **At 100M+ scale:** Qdrant officially states "a single node can typically hold up to about 100 million vectors" before requiring horizontal scaling
- **Payload overhead:** In-memory payload storage adds significant RAM for large payloads (text, images)
- **HNSW index memory:** The HNSW graph itself consumes additional RAM proportional to `m × max_level` per vector

### What Happens at 100M+ Scale
- Vertical scaling hits hardware limits (~4-8 TB RAM max on commodity servers)
- Must transition to distributed mode (horizontal scaling)
- **Distributed mode overhead:** Each shard requires separate memory for its HNSW index
- No automatic shard rebalancing in self-hosted OSS
- Qdrant recommends starting with 12 shards for future flexibility, but this limits throughput on small clusters

## 2. Disk-Based Search Limitations (mmap/on-disk)

### Mmap Storage Configuration
- Two options: `on_disk: true` at collection level, or `memmap_threshold` (segment-level auto-conversion)
- **Performance degradation:** "Graph traversal may require IO operations if you store the HNSW index on disk"
- **Cold-start penalty:** On-disk indexes require loading from disk/S3 on startup
- **NVMe requirement:** Qdrant recommends "fast NVMe storage" for on-disk workloads

### Known mmap Issues (from GitHub Issues)
- **Issue #9867:** WAL Segment::copy_to_path does not flush the copied mmap before returning (closed, but shows mmap flush issues exist)
- **Issue #9799:** Use-after-free in EncodedVectorsU8::get_quantized_vector_offset_and_code returns a slice into a freed buffer
- **Issue #9796:** Off-by-one in mmap sparse vector storage next_point_offset on reload with trailing deleted vector
- **Issue #9858:** Snapshot creation expands sparse gridstore pages: ~90x write amplification, background snapshots stall

### Payload Storage Limitations
- **InMemory payload:** All payload loaded into RAM at startup, expensive for large payloads
- **OnDisk payload:** "Access latency" is the downside; "checking values stored on disk might take too much time"
- **Workaround required:** Must create payload indexes for filtered fields, which then consume RAM regardless of storage type

## 3. Single-Node vs Distributed Scaling

### Single-Node Limitations
- ~100M vectors max per node (practical limit)
- No redundancy: "if you lose it, you lose both the data and the ability to serve it"
- Vertical scaling has natural hardware limits

### Distributed Mode Architecture
- **Minimum cluster size:** 3 nodes required for Raft consensus (fault tolerance)
- **Replication factor:** Must be ≥2 for production (minimum 3 nodes + RF=2)
- **Sharding model:** Manual shard assignment in self-hosted; automatic only in Qdrant Cloud
- **No automatic shard rebalancing in OSS:** "In self-hosted deployments, you must manually create or drop replicas and move shards between nodes as you scale"
- **Resharding:** Not supported without data migration; must plan shard count upfront
- **Network overhead:** Cross-shard queries add latency; no query routing optimization mentioned

### Scaling Weaknesses
- **Recommendation:** "Start with 12 shards" for flexibility, but "this approach can limit throughput on small clusters since each node manages multiple shards"
- **For optimal throughput:** "Set shard_number equal to your node count" (contradicts the 12-shard recommendation)
- **No streaming replication:** Must use snapshots for disaster recovery
- **gRPC issues between nodes:** Issue #9613 - "gRPC PointsInternal/QueryBatch 'Missing request message' on followers after upgrade to v1.18.x (p2p TLS)"

**Source URLs:**
- https://qdrant.tech/documentation/scaling/

## 4. Write Throughput Limitations

### Insert Rate at Scale
- **WAL (Write-Ahead Log):** All writes go through WAL first, then to segments
- **Optimizer contention:** "Larger segments take longer to build and recreate, slowing writes and optimization"
- **Segment merging:** Background optimization can compete with write operations
- **Batch upsert limits:** Strict mode can "cap batch upsert sizes" (configurable but limits throughput)

### Known Write Issues
- **Issue #9858:** Snapshot creation causes ~90x write amplification, background snapshots stall writes
- **Issue #9869:** Write operations accept timeout=0 despite OpenAPI schema declaring minimum: 1 (validation bug)
- **WAL replay can resurrect filter-deleted points** (Issue #9575, closed but indicates write path bugs)
- **Queue-proxifying a local shard can drop the shard** if transfer future cancelled after local.take() (Issue #9665)

### Bulk Ingestion Challenges
- **Issue #9117:** Feature request for "Deferred Sparse Index Building for Bulk Ingestion" - indicates current bulk write performance is suboptimal
- **Optimizer must rebuild HNSW graph** when adding payload indexes after data insertion
- **"It's more efficient to create [payload index] before indexing the data"** - but this isn't always practical

**Source URLs:**
- https://github.com/qdrant/qdrant/issues/9858
- https://github.com/qdrant/qdrant/issues/9117
- https://qdrant.tech/documentation/overview/ (Filtering section)

## 5. Startup Time / Recovery Time After Crash

### Cold-Start Problem (Major Known Issue)
- **Issue #9496 (Tracking Issue):** "[Tracking issue] Serverless cold-start optimization" - actively being worked on as of Jun 2026
- **Current approach:** "We have naive approach to loading cold-segment: we go component-by-component, loading configuration files, making a lot of individual read requests, which are not actually supposed to block each other"
- **Key optimization:** Two-pass segment open (prefetch files in parallel, then open from cache)
- **Still in progress:** Many sub-tasks listed as "partial" or "open"

### Crash Recovery Issues
- **Issue #9857:** "Rebuild corrupt Gridstore payload indexes on load instead of panicking (node crash-loops after power loss)"
  - After power loss, corrupt Gridstore blobs cause permanent crash loops
  - "With a 32-shard collection that takes ~35 min to load, each corrupt shard discovered costs another full crash cycle"
  - **Manual intervention required** to recover from corrupt indexes
- **Issue #9668:** "Cancelled shard snapshot recovery can leave a false dirty marker and load a healthy local shard as dummy after restart"
- **WAL recovery time:** For large collections, WAL replay can be slow
- **Collection stuck in YELLOW status:** Issue #8257 - "Collection stuck in YELLOW status with single replica cluster and excessive closed-* WAL files (v1.15.1)"

### Recovery Time Estimates
- 32-shard collection: ~35 minutes startup time (from Issue #9857)
- Corrupt shards add full crash cycle per shard discovered
- No parallel shard loading mentioned for recovery

## 6. Configuration Complexity and Operational Overhead

### Configuration Parameters (Extensive)
- `vectors.on_disk` / `memmap_threshold` / `indexing_threshold`
- `hnsw_config.on_disk` / `hnsw_config.m` / `hnsw_config.ef_construct`
- `optimizer_config` with multiple thresholds
- `on_disk_payload` per collection
- `shard_number` / `replication_factor` / `write_consistency_factor`
- `strict_mode` settings (multiple controls)
- Segment configuration (number of segments, size thresholds)

### Operational Complexity
- **No auto-scaling in OSS:** Must manually manage shards and replicas
- **No automatic shard rebalancing** in self-hosted deployments
- **Payload index timing matters:** "It's more efficient to create it before indexing the data" but retroactive creation requires segment reconstruction
- **HNSW graph rebuild required** when adding payload indexes after data is loaded (must toggle m=0 then back)
- **Strict mode not enforced by default in OSS:** "The OSS version does not enforce anything"
- **Configuration file vs API:** Settings can be set in config file or per-collection via API (two sources of truth)

### Monitoring Gaps
- **No built-in monitoring in OSS:** Only available in Cloud/Premium tiers
- **Community support only** for OSS users (Discord)
- **No automated backups** in OSS

## 8. Community Complaints

### GitHub Discussions
- **Discussion about 55M vectors:** Users seeking help optimizing search speed for large collections indicates performance challenges at scale
- **Index state confusion:** Users report "index state is green still there are left over indexed vectors" (confusion about optimizer behavior)
- **Cold-start complaints:** Multiple issues related to slow startup times and snapshot recovery

### Common Complaints (from issue patterns)
1. **Snapshot/WAL reliability:** Multiple issues about corruption, stall, and recovery failures
2. **Shard management complexity:** Race conditions in shard transfer, initialization, and cleanup
3. **Memory usage surprises:** Users hit RAM limits unexpectedly when collections grow
4. **Upgrade breakage:** v1.18.x upgrade caused gRPC communication failures between nodes
5. **Lack of auto-scaling:** Must manually manage shards in self-hosted
6. **Configuration confusion:** Multiple overlapping configuration mechanisms

### Support Limitations
- **OSS users:** Discord community only (best effort)
- **No SLA for community support**
- **Enterprise support:** Requires paid tier with response times (1h for Severity 1)

## 10. Features Missing vs Competitors

### vs Milvus
- **GPU acceleration:** Milvus has built-in GPU indexing; Qdrant has no GPU support mentioned
- **Automatic scaling:** Milvus (with Kubernetes operator) offers more automated scaling
- **Backup/Disaster Recovery:** Milvus has built-in backup; Qdrant requires snapshots
- **Index types:** Milvus supports IVF_FLAT, IVF_SQ8, IVF_PQ, SCANN, DISKANN, GPU_IVF_FLAT, GPU_IVF_PQ; Qdrant has HNSW only (plus quantization)

### vs Weaviate
- **Module system:** Weaviate has modular architecture for custom vectorizers
- **Multi-tenancy:** Both support it, but Weaviate's is more mature
- **GraphQL API:** Weaviate offers native GraphQL; Qdrant uses REST/gRPC

### vs pgvector
- **SQL integration:** pgvector integrates with existing PostgreSQL ecosystem
- **ACID transactions:** pgvector inherits PostgreSQL's transaction guarantees
- **Complex queries:** pgvector supports JOINs with relational data

### vs Pinecone (Managed)
- **Serverless:** Pinecone offers true serverless; Qdrant requires infrastructure management
- **Auto-scaling:** Pinecone handles scaling automatically
- **Global distribution:** Pinecone offers multi-region; Qdrant requires manual setup

### vs OpenSearch kNN
- **Ecosystem integration:** OpenSearch integrates with ELK stack
- **Hybrid search:** OpenSearch combines text + vector natively
- **Enterprise features:** OpenSearch has built-in security, alerting, anomaly detection

### Missing Features in Qdrant
1. **GPU acceleration** - No GPU indexing support
2. **Automatic shard rebalancing (OSS)** - Manual only in self-hosted
3. **Built-in monitoring (OSS)** - Only in Cloud/Premium
4. **Automated backups (OSS)** - Must use snapshots manually
5. **SQL/familiar query language** - API-only, no SQL layer
6. **Multi-region replication** - No built-in geo-distribution
7. **True serverless** - Requires always-on infrastructure
8. **Streaming ingestion** - No native streaming pipeline support
9. **ACID transactions** - No transaction support
10. **Built-in RBAC (OSS)** - Only in Cloud/Premium tiers

## Summary: Key Exploitable Weaknesses

### High-Impact Attack Vectors
1. **Cold-start time:** 35+ minutes for 32-shard collection; actively being worked on but not solved
2. **Crash recovery:** Power loss can cause permanent crash loops requiring manual intervention
3. **Memory cost at scale:** 100M vectors requires ~460 GB RAM (768-dim); expensive at scale
4. **No GPU acceleration:** Falls behind on hardware acceleration
5. **Operational complexity:** Manual shard management, no auto-scaling in OSS
6. **Write amplification:** 90x write amplification during snapshots
7. **SIMD waste:** Doesn't use AVX-512 on modern Intel hardware

### Competitive Positioning Opportunities
- **Price advantage:** Qdrant Cloud pricing is usage-based; position against compute costs
- **Simplicity:** Position against Qdrant's operational complexity
- **Reliability:** Highlight crash recovery and data durability concerns
- **Performance at scale:** 100M+ vector performance is a weakness
- **Enterprise features:** Many features locked behind paid tiers
