**Important note from Qdrant's FAQ:** Qdrant does NOT directly compare against FAISS/Annoy in their own benchmarks because "libraries like FAISS provide a great tool to do experiments with vector search, but they are far away from real usage in production environments." They use the same datasets as ann-benchmarks for alignment.

### Qdrant vs Competitors (from qdrant.tech/benchmarks/)

Qdrant's own comparative benchmarks (Jan/June 2024) on 4 datasets:

**Key findings:**
- **Qdrant achieves highest RPS and lowest latencies in almost all scenarios** across precision thresholds and metrics
- **4x RPS gains** observed on one dataset compared to previous runs
- **Elasticsearch:** Considerably faster than before but 10x slower on indexing (5.5 hrs vs 32 mins for 10M 96d vectors)
- **Milvus:** Fastest indexing time, maintains good precision, but not on-par with others at higher dimensions
- **Redis:** Good RPS at lower precision, latency scales poorly with parallelism
- **Weaviate:** Improved the least since previous benchmarks

### Qdrant vs Elasticsearch DiskBBQ (July 2026)

On 21M vectors, 768d, wiki_dpr_e5 dataset:

| Engine | Config | Recall@100 | Throughput | Avg Latency | P99 Latency |
|---|---|---|---|---|---|
| Elasticsearch DiskBBQ | 3x 7vCPU/26GB, RF=2 | 0.9599 | 32.4 QPS | 122.6ms | 184.3ms |
| Qdrant (two-stage) | 3x 2vCPU/8GB, RF=1 | 0.9596 | 67.2 QPS | 59.5ms | 86.0ms |
| Qdrant (two-stage) | 3x 4vCPU/16GB, RF=1 | 0.9596 | 111.9 QPS | 35.7ms | 83.1ms |

**Qdrant: 2.1x throughput, 51% lower latency, on 1/3 the compute resources.**

**Source:** https://qdrant.tech/blog/benchmark-elastic-diskbbq/

## 5. Multi-threaded Search Scaling (QPS vs Thread Count)

### dbpedia-openai-1M-1536d Scaling Analysis

From raw benchmark data, comparing single-thread vs 100-thread:

| Config | 1-thread QPS | 100-thread QPS | Scaling Factor |
|---|---|---|---|
| BQ, m=32, ef=128, ~0.95 recall | 459 | 1,202 | 2.6x |
| SQ, m=16, ef=128, ~0.95 recall | 429 | 1,193 | 2.8x |
| F32, m=16, ef=128, ~0.97 recall | 346 | 1,260 | 3.6x |
| SQ, m=32, ef=256, ~0.98 recall | 288 | 1,226 | 4.3x |
| SQ, m=32, ef=512, ~0.99 recall | 244 | 1,215 | 5.0x |
| SQ, m=64, ef=512, ~0.995 recall | 129 | 944 | 7.3x |
| F32, m=32, ef=512, ~0.999 recall | 123 | 316 | 2.6x |

**Key observations:**
- At moderate recall (0.95-0.98), scaling from 1 to 100 threads yields **2.6-4.3x** improvement
- Higher precision targets scale better (up to 7.3x) because there's more parallelism opportunity
- At very high recall (>0.999), scaling diminishes as the search becomes graph-traversal bound
- The 100-thread numbers represent the RPS ceiling on an 8-vCPU machine

## 6. Filtered Vector Search Performance

### Qdrant's Filterable HNSW Approach

Qdrant uses a **unique approach** to filtered search that avoids the pitfalls of pre-filtering and post-filtering:

- **Pre-filtering:** Requires binary mask of entire dataset; doesn't scale (mask grows linearly)
- **Post-filtering:** Loses results or requires many candidates; accuracy collapses
- **Qdrant's approach:** Modifies HNSW graph traversal to apply filters during search itself, maintaining graph connectivity

**Source:** https://qdrant.tech/articles/filterable-hnsw/

### Filtered Search Benchmark Results

From Qdrant's filtered search benchmark (Feb 2023, updated):

**Three observed patterns across engines:**
1. **Speed boost** -- filtered search faster than unfiltered (when filter is restrictive enough to avoid vector index entirely)
2. **Speed downturn** -- some engines struggle with filtering masks
3. **Accuracy collapse** -- some engines lose accuracy dramatically under certain filters (HNSW graph becomes disconnected)

**Qdrant avoids all three problems** through:
- Query planning strategy that chooses optimal search path
- Category-aware graph connectivity
- Numerical range bucketing with neighbor connections

**Datasets available for reproduction:** https://github.com/qdrant/ann-filtering-benchmark-datasets

### Filtered Search Performance Data

From Qdrant's benchmark page, at the same recall target:
- Qdrant typically shows **speed boost** (faster with filters) for restrictive filters
- Competing engines show 2-10x slowdown under selective filters
- Some engines lose >50% recall under aggressive filters

## 7. TurboQuant Benchmark Numbers vs SQ/BQ

### TurboQuant Overview (Qdrant 1.18, May 2026)

TurboQuant is based on Google Research's algorithm with Qdrant enhancements:
- Fast Hadamard rotation before compression
- Length renormalization (from RaBitQ paper)
- Per-coordinate calibration pre-pass
- SIMD-accelerated implementation

### TQ4 vs SQ Performance

| Metric | SQ (Scalar Quantization) | TQ4 (TurboQuant 4-bit) |
|---|---|---|
| Compression ratio | 4x (float32 -> int8) | 8x (float32 -> 4-bit) |
| Recall@10 (avg across datasets) | ~0.92 | ~0.92 |
| Speed | Baseline | Similar to SQ |
| Memory | 4x reduction | **8x reduction** |

**TQ4 achieves similar recall and speed to SQ at DOUBLE the compression ratio.**

### TQ1 vs BQ Performance

| Metric | BQ (Binary Quantization) | TQ1 (TurboQuant 1-bit) |
|---|---|---|
| Storage | 1 bit per dimension | 1 bit per dimension |
| Recall@10 (avg across datasets) | ~0.59 | ~0.72 |
| Speed | Faster | Slightly slower |

**TQ1 outperforms BQ by 10-20 percentage points in recall at equivalent storage.**

### DiskBBQ Benchmark (Qdrant vs Elasticsearch, July 2026)

On 21M x 768d vectors with TurboQuant 4-bit:
- **Qdrant: 67.2 QPS, 59.5ms avg, 86ms p99** (on 3x 2vCPU/8GB nodes)
- **Elasticsearch DiskBBQ: 32.4 QPS, 122.6ms avg, 184ms p99** (on 3x 7vCPU/26GB nodes)

**Source:** https://qdrant.tech/blog/benchmark-elastic-diskbbq/

| Dataset | Engine Config | Upload Time | Index Build |
|---|---|---|---|
| glove-100-angular | qdrant-m-64-ef-512 | 29s | ~31s total |
| glove-100-angular | qdrant-m-32-ef-256 | 33s | ~33s total |

| dbpedia-openai-1M-1536 | qdrant-bq-m-32-ef-128 | 52s | ~52s total |
| dbpedia-openai-1M-1536 | qdrant-sq-m-32-ef-256 | 53s | ~53s total |
| dbpedia-openai-1M-1536 | qdrant-sq-m-64-ef-512 | 57s | ~57s total |
| dbpedia-openai-1M-1536 | qdrant-m-32-ef-256 | 33s | ~33s total |
| gist-960-euclidean | qdrant-m-16-ef-128 | 32s | ~32s total |
| deep-image-96-angular (10M) | elasticsearch-m-16-ef-128 | 2,425s | 18,502s total |

### Key Observations on Index Build

- **Milvus is fastest for indexing** according to Qdrant's observations
- **Elasticsearch can be 10x slower** for indexing 10M+ vectors (5.5 hrs vs 32 mins)
- **Qdrant indexing scales with ef_construct** -- higher ef = slower build but better search quality
- **SQ adds ~23-31% to upload time** due to quantization pass
- **BQ adds minimal overhead** -- similar upload times to F32

### BQ-Optimized Upload Pattern (from Qdrant docs)

The recommended pattern for large-scale upload:
1. Create collection with HNSW m=0 (disable graph), enable BQ
2. Upload all vectors (fast, no graph construction)
3. Enable HNSW graph construction (m=16)

This two-phase approach significantly reduces upload time for large datasets.
