## 1. Exact Distance Computation: Cosine/L2/Dot Product

### Float32 Vectors (Unquantized Path)

Qdrant's float32 distance computation is in `lib/segment/src/spaces/simple.rs` with SIMD backends in `simple_avx.rs` (x86_64) and `simple_neon.rs` (aarch64).

**Core formulas (scalar fallback):**
```rust
// Dot product: v1 · v2
fn dot_similarity(v1: &[f32], v2: &[f32]) -> f32 {
    v1.iter().zip(v2).map(|(a, b)| a * b).sum()
}

// Euclidean (L2): -||v1 - v2||² (negated so larger = closer)
fn euclid_similarity(v1: &[f32], v2: &[f32]) -> f32 {
    -v1.iter().zip(v2).map(|(a, b)| (a - b).powi(2)).sum::<f32>()
}

// Manhattan (L1): -Σ|v1_i - v2_i|
fn manhattan_similarity(v1: &[f32], v2: &[f32]) -> f32 {
    -v1.iter().zip(v2).map(|(a, b)| (a - b).abs()).sum()
}

// Cosine: normalize first, then dot product
fn cosine_preprocess(vector: DenseVector) -> DenseVector {
    let length = vector.iter().map(|x| x * x).sum::<f32>().sqrt();
    vector.iter().map(|x| x / length).collect()
}
```

**Key insight:** Qdrant negates L2 and L1 similarities so that larger values always mean "closer" — a unified convention across all metrics. Cosine is implemented as "normalize to unit sphere, then dot product" with the normalization done once at preprocess time.

**Runtime dispatch** (from `simple.rs`):
```rust
// CosineMetric::similarity delegates to DotProductMetric::similarity
// after preprocess() normalizes vectors

fn similarity(v1, v2) -> ScoreType {
    #[cfg(target_arch = "x86_64")]
    if is_x86_feature_detected!("avx") && is_x86_feature_detected!("fma")
       && v1.len() >= 32 {
        return unsafe { euclid_similarity_avx(v1, v2) };
    }
    // SSE fallback for 16+ dims, NEON fallback for aarch64, scalar otherwise
    euclid_similarity(v1, v2)
}
```

Minimum SIMD threshold: 32 dims for AVX, 16 dims for SSE/NEON.

## 2. SIMD Kernels: AVX2, AVX-512, ARM NEON

### 2a. Float32 Kernels (Unquantized)

**AVX2 + FMA** (`simple_avx.rs`):
- Processes **32 floats per iteration** with 4x loop unrolling (8 floats × 4 accumulators)
- Uses `_mm256_fmadd_ps` (fused multiply-add) for dot product
- Uses `_mm256_andnot_ps` with sign-bit mask for abs() in Manhattan
- Horizontal sum via `_mm256_hadd_ps` after extracting 128-bit lanes

```rust
// Dot product hot loop (4x unrolled, 32 floats/iter):
while i < m {
    sum256_1 = _mm256_fmadd_ps(_mm256_loadu_ps(ptr1), _mm256_loadu_ps(ptr2), sum256_1);
    sum256_2 = _mm256_fmadd_ps(_mm256_loadu_ps(ptr1+8), _mm256_loadu_ps(ptr2+8), sum256_2);
    sum256_3 = _mm256_fmadd_ps(_mm256_loadu_ps(ptr1+16), _mm256_loadu_ps(ptr2+16), sum256_3);
    sum256_4 = _mm256_fmadd_ps(_mm256_loadu_ps(ptr1+24), _mm256_loadu_ps(ptr2+24), sum256_4);
    ptr1 += 32; ptr2 += 32; i += 32;
}
```

**ARM NEON** (`simple_neon.rs`):
- Processes **16 floats per iteration** with 4x unrolling (4 floats × 4 accumulators)
- Uses `vfmaq_f32` for fused multiply-add
- Uses `vaddvq_f32` for horizontal sum (single instruction on ARMv8)
- Cosine normalization uses `vmulq_f32` with broadcast `1/length`

### 2b. INT8 Scalar Quantization Kernels

Located in `lib/quantization/src/encoded_vectors_u8.rs`:

**Dot product (L2/Cosine):**
```rust
// Scalar fallback:
fn impl_score_dot(q_ptr: *const u8, v_ptr: *const u8, actual_dim: usize) -> i32 {
    let mut score = 0i32;
    for i in 0..actual_dim {
        score += i32::from(*q_ptr.add(i)) * i32::from(*v_ptr.add(i));
    }
    score
}
```

SIMD implementations are in external ASM files (linked via `extern "C"`):
- `impl_score_dot_avx` — AVX2 integer dot product
- `impl_score_dot_sse` — SSE4.1 integer dot product  
- `impl_score_dot_neon` — ARM NEON integer dot product

**Post-processing for Cosine:**
```rust
// multiplier = alpha² (from quantization bounds)
// score = multiplier * int_dot + query_offset + vector_offset
fn postprocess_score(&self, score: f32, query_offset: f32, vector_offset: f32) -> f32 {
    self.multiplier * score + query_offset + vector_offset
}
```

## 3. HNSW Traversal vs Reranking Scoring

### Two Scoring Paths, One Artifact

Qdrant maintains **two distinct scoring paths** that share a single quantized artifact:

**Path 1: Asymmetric scoring (user search / HNSW traversal)**
- Query: original float32 vector, Hadamard-rotated but NOT quantized
- Stored: TurboQuant-encoded vector
- Scoring: `dotprod(precomputed_query, quantized_vector) * scaling_factor`
- This is the path used during HNSW graph traversal at query time
- Anisotropy compensation IS applied (query-side only, free)

**Path 2: Symmetric scoring (HNSW build, segment merges, internal operations)**
- Both sides: TurboQuant-encoded vectors
- Scoring: `score_4bit_internal(data_v1, data_v2)` (centroid-space dot product)
- No anisotropy compensation (would amplify quantization noise from both sides)
- Graph topology optimized for "encoding-compensated space"

```rust
// From turboquant/quantization.rs:
fn score_internal(&self, i: PointOffsetType, j: PointOffsetType) -> f32 {
    let v1 = self.encoded_vectors.get_vector_data(i);
    let v2 = self.encoded_vectors.get_vector_data(j);
    // Symmetric: both quantized
    self.quantizer.score_symmetric(&v1, &v2)
}

fn score_bytes(&self, query: &EncodedQueryTQ, bytes: &[u8]) -> f32 {
    // Asymmetric: precomputed query vs quantized vector
    self.quantizer.score_precomputed(query, bytes)
}
```

### Rescoring Pattern

The `QuantizedQueryScorer` in `quantized_query_scorer.rs` wraps the quantized storage and provides the `QueryScorer` trait used by HNSW traversal:

```rust
fn score_stored(&self, idx: PointOffsetType) -> ScoreType {
    self.quantized_data.score_point(&self.query, idx, &self.hardware_counter)
}

fn score_stored_batch(&self, ids: &[PointOffsetType], scores: &mut [ScoreType]) {
    // Batch scoring for HNSW neighbor evaluation
    for (idx, vector) in self.quantized_data.iter_batch(ids) {
        scores[idx] = self.quantized_data.score(&self.query, &vector, ...);
    }
}
```

The `RawScorerImpl` wraps any `QueryScorer` and is used by the HNSW graph traversal code. After graph traversal collects `ef` candidates, a separate f32 reranking pass can be triggered using the original vectors.

## 4. INT8 Quantization Scoring Path

### Encoding

```rust
// From encoded_vectors_u8.rs:
fn encode_value(&self, value: f32) -> u8 {
    let i = (value - self.offset) / self.alpha;
    i.clamp(0.0, 127.0).round() as u8
}
// alpha = (max - min) / 127.0, offset = min
```

### Storage Layout
- Each vector: `[f32_vector_offset | u8 quantized_bytes padded to 16-byte alignment]`
- `ADDITIONAL_CONSTANT_SIZE = 4` bytes (f32 offset per vector)
- `ALIGNMENT = 16` (dim rounded up to next multiple of 16)

### Scoring Formula
```rust
// Raw integer dot: Σ q_i8[i] × v_i8[i]
// Post-process: multiplier × raw_dot + query_offset + vector_offset

// For Cosine/Dot: multiplier = alpha²
// For L1: multiplier = alpha
// For L2: multiplier = -2 × alpha²

// query_offset = Σ(encoded_query[i]) × alpha × offset  (for Dot/Cosine)
// vector_offset = Σ(encoded_vector[i]) × alpha × offset + actual_dim × offset²
```

### SIMD Dispatch (runtime feature detection)
```rust
fn score_bytes(&self, query, bytes, hw_counter) -> f32 {
    #[cfg(target_arch = "x86_64")]
    if is_x86_feature_detected!("avx2") && is_x86_feature_detected!("fma") {
        return self.score_point_avx(query, bytes);
    }
    if is_x86_feature_detected!("sse4.1") {
        return self.score_point_sse(query, bytes);
    }
    #[cfg(all(target_arch = "aarch64", target_feature = "neon"))]
    if std::arch::is_aarch64_feature_detected!("neon") {
        return self.score_point_neon(query, bytes);
    }
    self.score_point_simple(query, bytes)  // scalar fallback
}
```

## 5. TurboQuant Scoring Kernels (pshufb + maddubs Pattern)

### The Core SIMD Pattern for 4-bit TQ

The 4-bit TurboQuant kernel uses a **codebook lookup + multiply-accumulate** pattern that maps perfectly to x86 SIMD:

**Step 1: Nibble extraction + index unpacking**
```rust
// From query4bit/x64.rs:
let v_packed = _mm_loadl_epi64(vector_ptr);  // Load 8 bytes (16 nibbles)
let v_lo = _mm_and_si128(v_packed, nibble_mask);   // Low nibbles
let v_hi = _mm_and_si128(_mm_srli_epi16(v_packed, 4), nibble_mask); // High nibbles
let v = _mm_unpacklo_epi8(v_lo, v_hi);  // Interleave into 16 indices
```

**Step 2: Codebook lookup via pshufb**
```rust
// CODEBOOK_U8 = [0, 31, 52, 69, 84, 97, 110, 122, 134, 146, 159, 172, 187, 204, 225, 255]
// u8 codebook for x86 (unsigned, matches maddubs input requirement)
let codebook = _mm_loadu_si128(CODEBOOK_U8.as_ptr().cast::<__m128i>());
let c_u = _mm_shuffle_epi8(codebook, v);  // pshufb: 16 codebook lookups in 1 instruction
```

**Step 3: Multiply-accumulate via maddubs + madd_epi16**
```rust
// Query is split into [low, high] i8 halves
// q_signed = 128 × high + low  (QUERY_HIGH_COEF = 128 on x86)
let prod_low = _mm_maddubs_epi16(c_u, q_low);   // u8 × i8 → i16 pair-sum
let prod_high = _mm_maddubs_epi16(c_u, q_high);
acc_low = _mm_add_epi32(acc_low, _mm_madd_epi16(prod_low, ones));  // i16 pair-sum → i32
acc_high = _mm_add_epi32(acc_high, _mm_madd_epi16(prod_high, ones));
```

**Step 4: Reconstruction**
```rust
// Final score = postprocess_scale × (dot_raw - bias_correction)
// bias_correction = 128 × Σ q_signed  (undoes the unsigned shift)
let dot_raw = hsum_i32(acc_low) + 128 * hsum_i32(acc_high);
let score = postprocess_scale * (dot_raw as f32 - bias_correction as f32);
```

### AVX2 Version
- Processes **32 dimensions per iteration** (2 × 16-dim chunks in YMM)
- Same pshufb + maddubs pattern, but `_mm256_shuffle_epi8` broadcasts codebook to both lanes
- `_mm256_maddubs_epi16` processes both low and high query halves in one instruction

### AVX-512 VNNI Version
- Processes **64 dimensions per iteration** (4 × 16-dim chunks in ZMM)
- Uses `VPDPBUSD` (Vector Packed Dword Unsigned Byte with Signed saturation) — a single instruction that does u8×i8 dot product with i32 accumulation
- 2 chunks per VNNI iteration vs 1 chunk per AVX2 iteration

### ARM NEON Version
- Uses `vmull_s8` (signed × signed, no offset needed on ARM)
- Codebook stored as signed i8 directly (CODEBOOK_I8)
- Optional `sdot` instruction on ARMv8.2-A for int8 dot product

### Weighted Version (TQ+ Symmetric Scoring)
For TQ+ error correction's `D'²` weighting:
```rust
// c_a × c_b in i16, then multiply by i16 weights
let prod_lo = _mm256_mullo_epi16(c_a_lo, c_b_lo);
let prod_hi = _mm256_mullo_epi16(c_a_hi, c_b_hi);
let pw_lo = _mm256_madd_epi16(prod_lo, w_lo);  // pair-sum with weights
// Accumulate into i64 to avoid overflow at large dims
let pw_lo_i64 = _mm256_cvtepi32_epi64(_mm256_castsi256_si128(pw));
```

## 6. Query Vector Handling

### Normalize Once, Per-Query (Not Per-Shard)

**Query preprocessing is done once per search request**, not per segment/shard:

```rust
// From quantized_query_scorer.rs:
pub fn new<TElement, TMetric>(raw_query, quantized_data, quantization_config, hw_counter) {
    // 1. Apply metric-specific preprocessing (e.g., L2-normalize for Cosine)
    let raw_preprocessed_query = TMetric::preprocess(raw_query);
    
    // 2. Convert to element type
    let original_query = TElement::slice_from_float_cow(Cow::Owned(raw_preprocessed_query));
    
    // 3. Apply quantization preprocessing (if needed)
    let original_query_prequantized = TElement::quantization_preprocess(
        quantization_config, TMetric::distance(), original_query,
    );
    
    // 4. Encode query (Hadamard rotation + integer quantization for TQ)
    let query = quantized_data.encode_query(&original_query_prequantized);
    // This EncodedQuery is then reused for ALL scored vectors in this search
}
```

**For TurboQuant specifically**, the query encoding in `precompute_query()`:
```rust
pub fn precompute_query(&self, query: &[f32]) -> EncodedQueryTQ {
    // 1. Pad to padded_dim
    // 2. Apply Hadamard rotation (O(D log D))
    // 3. For TQ+: divide by per-coord scale, stash ec_correction
    // 4. Quantize to integer form (Query4bitSimd, Query2bitSimd, etc.)
    // Result: precomputed query reused for ALL vectors in this search
}
```

**The query is precomputed once and the EncodedQuery is passed to every `dotprod()` call.** This means:
- Hadamard rotation: O(D log D) once per query
- Integer quantization: O(D) once per query
- Per-vector scoring: O(D/simd_width) per comparison

**Per-shard handling:** When searching across multiple segments, each segment has its own `QuantizedVectorStorage` with its own quantization metadata (alpha, offset, error correction parameters). The query preprocessing happens before segment iteration, and the same preprocessed query is scored against each segment's quantized vectors. However, for TQ+ with per-segment error correction, the `ec_correction` is segment-specific — but this is handled by the scalar correction term added after the SIMD raw dot.

## 7. Memory Access Patterns in the Hot Path

### Sequential, Cache-Friendly Access

**Quantized vectors are stored contiguously in memory** (RAM or mmap), enabling sequential prefetch:

```rust
// From encoded_storage.rs: vectors are stored as a flat byte array
// Each vector is `quantized_vector_size()` bytes
// Sequential access during batch scoring:
fn iter_batch(&self, offsets: &[PointOffsetType]) -> impl Iterator<Item = (usize, Cow<[u8]>)> {
    // Yields (point_id, vector_bytes) pairs
    // For mmap storage: OS page cache handles prefetching
    // For RAM storage: vectors are contiguous in heap
}
```

**INT8 vectors at 1536-dim:** 1556 bytes each (1536 + 16 alignment + 4 offset). L2 cache (256KB-1MB) fits ~170-680 vectors. At typical HNSW fan-out (m=16), the working set for one graph level is well within L2.

**TurboQuant 4-bit at 1536-dim:** 772 bytes each. L2 fits ~340-1380 vectors. Much better cache utilization.

**SIMD data access pattern:**
- Query data: loaded once from stack (`query_data: Vec<[[i8; 16]; 2]>`)
- Vector data: sequential byte reads from contiguous storage
- Codebook: single 16-byte L1-resident load (broadcast to all SIMD lanes)
- Weights (TQ+): sequential i16 reads from per-segment metadata

**The hot inner loop for 4-bit TQ:**
```rust
// 16 dimensions per iteration on SSE, 32 on AVX2, 64 on AVX-512
// Vector data: 8 bytes per 16-dim chunk (2 nibbles per byte)
// Query data: 32 bytes per 16-dim chunk ([low, high] × 16 × i8)
// Total memory traffic per 16 dims: 8 + 32 = 40 bytes
// Compute: 1 pshufb + 2 maddubs + 2 madd_epi16 + 2 add_epi32 = ~7 ops
// Arithmetic intensity: ~7 ops / 40 bytes = 0.175 ops/byte (memory-bound)
```

**For mmap-backed vectors:** Qdrant uses `io_uring` on Linux for async disk I/O, prefetching quantized candidates from disk while rescoring against on-disk original vectors.

### Key Optimization: No Per-Vector Branch in Hot Path

The SIMD dispatch happens once at `score_bytes()` entry, not per-vector. The `#[target_feature]` annotations on each backend ensure the compiler generates optimal code without runtime checks inside the loop.

## 8. Batch/Multi-Query Search Implementation

### Batch Scoring

Qdrant's batch scoring is implemented via the `score_stored_batch` method on `QueryScorer`:

```rust
// From quantized_query_scorer.rs:
fn score_stored_batch(&self, ids: &[PointOffsetType], scores: &mut [ScoreType]) {
    // Vector I/O tracking
    self.hardware_counter.vector_io_read()
        .incr_delta(ids.len() * self.quantized_data.quantized_vector_size());
    
    // Sequential batch scoring
    for (idx, vector) in self.quantized_data.iter_batch(ids) {
        scores[idx] = self.quantized_data.score(&self.query, &vector, &self.hardware_counter);
    }
}
```

**For float32 vectors:**
```rust
// From metric_query_scorer.rs (via RawScorer):
fn score_stored_batch(&self, ids: &[PointOffsetType], scores: &mut [ScoreType]) {
    self.vector_storage.for_each_in_batch(ids, |idx, vector| {
        scores[idx] = self.query.score_by(|example| {
            TMetric::similarity(example, vector)
        });
    });
}
```

### Multi-Vector (ColBERT-style) Scoring

```rust
// From multi_metric_query_scorer.rs:
fn score_stored_batch(&self, ids: &[PointOffsetType], scores: &mut [ScoreType]) {
    self.vector_storage.for_each_in_batch_multi(ids, |idx, vector| {
        scores[idx] = self.score_ref(vector);  // MaxSim over sub-vectors
    });
}
```

### HNSW Neighbor Scoring

The HNSW graph traversal uses `RawScorer::score_points()` which calls `score_stored_batch()`:
```rust
fn score_points(&self, points: &[PointOffsetType], scores: &mut [ScoreType]) {
    assert_eq!(points.len(), scores.len());
    self.query_scorer.score_stored_batch(points, scores);
}
```

**No explicit multi-query (batch of different queries) optimization exists** in the current codebase. Each query creates its own `RawScorer` with a precomputed query. Parallelism is achieved at the segment level (multiple segments scored concurrently) rather than at the query level.

| Backend | Dimensions/iter | Key instruction | Latency (cycles) |

| SSE4.1 | 16 | `_mm_maddubs_epi16` | 1 |
| AVX2 | 32 | `_mm256_maddubs_epi16` | 1 |
| AVX-512 VNNI | 64 | `VPDPBUSD` | 1 (fused) |
| ARM NEON | 16 | `vmull_s8` | 1 |
| ARM SDOT | 16 | `sdot` | 1 (fused) |

**The 4-bit TQ kernel processes 16 dimensions per maddubs instruction** (2 nibbles × 8 bytes input = 16 codebook lookups). For 1536-dim vectors:
- SSE: 96 iterations × ~7 instructions = ~672 instructions
- AVX2: 48 iterations × ~7 instructions = ~336 instructions
- AVX-512 VNNI: 24 iterations × ~5 instructions = ~120 instructions

### Codebase Profiling Infrastructure

Qdrant has a `HardwareCounterCell` that tracks:
- `cpu_counter`: total dimension operations (for FLOP estimation)
- `vector_io_read`: bytes read from storage (for I/O accounting)

These counters are incremented in every scoring path but are used for observability, not published benchmarks.

## Summary: Key Takeaways for DB-Strike

### What Qdrant Does Well
1. **pshufb + maddubs pattern** is the optimal SIMD kernel for 4-bit codebook scoring — single-instruction codebook lookup + multiply-accumulate
2. **Query precomputed once** and reused for all vectors — rotation + quantization is O(D log D) amortized over N vectors
3. **Two-path scoring** (symmetric for build, asymmetric for search) is architecturally clean
4. **Contiguous storage** with sequential access patterns — L2 cache friendly for quantized vectors
5. **Multi-tier SIMD dispatch** with runtime feature detection (AVX-512 → AVX2 → SSE → scalar)

### What Qdrant Does NOT Publish
1. **No QPS benchmarks** for TurboQuant at 1M+ scale
2. **No p99 latency measurements** for quantized search
3. **No per-instruction throughput analysis** of their SIMD kernels
4. **No cache miss profiling** or memory bandwidth analysis

### Opportunities for DB-Strike
1. **Benchmark and publish concrete QPS numbers** — Qdrant's omission here is a gap we can fill
2. **AVX-512 VNNI** is the fastest path (2x throughput over AVX2) — ensure it's enabled
3. **ARM SDOT** support is critical for Graviton4/Ampereltra deployments
4. **Weighted kernel (TQ+) needs i64 accumulation** — overflow at 64K dims if using i32
5. **No multi-query batch optimization** — scoring multiple queries against the same vector set is a potential win
