# F4: Qdrant Filtering & Hybrid Search Capabilities - Deep Research

## 1. Filterable HNSW Implementation Details

### Core Concept: In-Graph Filtering via Extra Edges

Qdrant's key innovation is the **Filterable HNSW Index** (available since v1.1.1). Rather than treating filtering as a separate step, Qdrant extends the standard HNSW graph with **additional edges based on indexed payload values**.

**How it works:**
- Standard HNSW builds edges between vectors that are close in embedding space
- Qdrant adds **extra edges** during graph construction that connect vectors sharing the same payload values (e.g., same category, same tenant)
- During search, the traversal can "hop" along both similarity edges AND payload-aware edges
- This allows the graph to remain navigable even when strict filters are applied

**Key implementation details:**
- Extra edges are added **for each payload index separately**, not for every combination of payload indices
- The HNSW graph must be built **after** payload indexes are created for the extra edges to be generated
- If a payload index is created after data ingestion, the HNSW index must be rebuilt (by changing `ef_construct` by 1)
- The `enable_hnsw` parameter (v1.17.0) lets you disable extra edge creation for payload fields that are only used for sparse vector search (since sparse search is exact and doesn't use HNSW)

**Configuration parameters:**
- `ef_construct` - HNSW construction parameter (higher = more edges, better recall, more memory)
- `m` - Number of bi-directional links per node in HNSW
- `ef` (at search time via `hnsw_ef`) - Controls search accuracy vs speed tradeoff
- `full_scan_threshold` - Below this count, full scan is used instead of HNSW

## 2. Pre-Filter vs Post-Filter vs In-Graph Filtering

### Qdrant's Approach: Dynamic Query Planning (In-Graph Filtering)

Qdrant does **NOT** use simple pre-filter or post-filter approaches. Instead, it uses a **Query Planner** that dynamically selects the optimal strategy per segment:

#### Query Planning Strategies (per segment):

1. **Full Scan** - Used when the number of points is below a configurable threshold. Simple linear scan with filter check.

2. **Payload Index Retrieval** - When filter cardinality is **low** (selective filter), Qdrant uses the payload index to retrieve matching point IDs first, then scores only those points. This is essentially a **pre-filter** approach.

3. **Filterable HNSW (In-Graph)** - When filter cardinality is **high** (weak filter), Qdrant uses the HNSW graph with extra payload-aware edges. The filter is applied **during** graph traversal - not before, not after. This is the **in-graph filtering** approach.

4. **ACORN (v1.16.0)** - When selectivity is **low** (strict filter) but cardinality is still **high** (too many points for payload-index-only approach), ACORN explores **neighbors of neighbors** (2-hop) when direct neighbors are filtered out. This improves recall at the cost of 2-10x performance.

#### Strategy Selection Logic:

```
Estimated filter selectivity = Estimated matching points / Total points
```

- **High selectivity** (most points pass filter): Use HNSW normally
- **Medium selectivity**: Use filterable HNSW with extra edges
- **Low selectivity + high cardinality**: Use ACORN algorithm
- **Low selectivity + low cardinality**: Use payload index for pre-filter
- **Very small segments**: Full scan

The query planner runs **independently per segment** and uses heuristics that can vary between Qdrant versions. Thresholds are configurable via config files.

**Critical insight:** This is fundamentally different from Weaviate's approach (which uses a fixed pre-filter-then-search strategy) or Milvus's approach (which has limited filter-aware graph construction).

## 3. Payload Index Implementation

### Index Types and Data Structures

Qdrant's payload index is similar to traditional database indexes, built per field and type:

| Index Type | Data Structure | Supports | Notes |
|------------|---------------|----------|-------|
| `keyword` | Hash map / inverted index | Match, Match Any, Match Except | Exact value lookup |
| `integer` | Parameterized (lookup + range) | Match, Range | Can disable lookup or range to save memory |
| `float` | Range index | Range only | |
| `bool` | Match index (v1.4.0+) | Match | |
| `geo` | Geo spatial index | Geo Bounding Box, Geo Radius | |
| `datetime` | Range index (v1.8.0+) | Range | |
| `text` | Full-text inverted index | Full-text Match | Tokenization: word, whitespace, prefix, multilingual |
| `uuid` | Optimized keyword (v1.11.0+) | Match | Optimized for UUID patterns |

### Advanced Index Features:

1. **Parameterized Integer Index (v1.8.0)** - Can disable `lookup` or `range` independently to reduce memory usage in large collections

2. **On-Disk Payload Index (v1.11.0)** - For rarely-used or large payload indexes, can be stored on disk. Affects cold request latency due to disk I/O.

3. **Tenant Index (v1.11.0)** - For multitenancy scenarios. Localizes tenant-specific data on disk for faster tenant-filtered searches. Works with `keyword` and `uuid` types.

4. **Principal Index (v1.11.0)** - Optimizes storage for fields that are the primary filter (e.g., timestamps). Works with `integer`, `float`, `datetime`.

5. **Cardinality Estimation** - Payload indexes are used to accurately estimate filter cardinality, which drives the query planner's strategy selection.

### Memory Impact:
- Payload indexes occupy additional memory and disk space
- Only recommended for fields used in filtering
- If memory constrained, index the field that limits results the most (highest cardinality)
- Unindexed fields: Qdrant provides `strict mode` with `unindexed_filtering_retrieve: false` to block queries on unindexed fields

**Source:** https://qdrant.tech/documentation/manage-data/indexing/#payload-index
**Source:** https://qdrant.tech/documentation/manage-data/indexing/#tenant-index

## 4. Performance of Filtered Search at Various Selectivities

### Known Performance Characteristics:

**Qdrant's own documentation acknowledges the following pattern:**

| Selectivity | Strategy Used | Expected Behavior |
|-------------|--------------|-------------------|
| High (>50%) | Standard HNSW | Near-native HNSW performance |
| Medium (10-50%) | Filterable HNSW (extra edges) | Good performance, slight recall drop possible |
| Low (1-10%) | ACORN or Payload Index | ACORN: 2-10x slower but better recall; Payload index: fast but limited |
| Very Low (<1%) | Payload Index + Rescore | Fast candidate retrieval, then exact scoring |

### Precision by M (Graph Connectivity):

Qdrant's documentation includes a chart showing that **recall drops significantly** as filter strictness increases, especially when `m` (graph connectivity) is low. Higher `m` values improve filtered search recall but increase memory usage.

### ACORN Performance Impact:
- **2-10x slower** than standard HNSW in typical scenarios
- Activates conditionally when `estimated_selectivity < max_selectivity` (default: 0.4)
- Significantly improves recall for restrictive filters
- The tradeoff is configurable: `max_selectivity` from 0.0 (never use ACORN) to 1.0 (always use ACORN)

### No Published Benchmark Numbers:
Qdrant does **not publish specific benchmark numbers** for filtered search at different selectivities in their documentation. Their benchmark page (https://qdrant.tech/benchmarks/) focuses on overall throughput/latency comparisons with other databases.

## 5. Sparse Vector / Hybrid Search Implementation

### Sparse Vector Support (v1.7.0+)

**Storage format:**
```json
{
    "indices": [1, 3, 5, 7],    // uint32 indices
    "values": [0.1, 0.2, 0.3, 0.4]  // float32 values
}
```

**Key characteristics:**
- Sparse vectors have **no fixed length** - dynamically allocated during insertion
- Maximum non-zero values limited to u32 range (4,294,967,295)
- Stored in **separate sparse vector storage** with dedicated index
- Sparse vector index is **exact** (no approximation) - always returns correct results
- Sparse search speed is proportional to the number of non-zero values in the query
- Only supports **dot product** similarity (not cosine, euclidean, etc.)
- Sparse vectors are **immediately indexed** in the mutable version of the sparse index
- Immutable sparse index is built during the same optimization process as dense vectors

### IDF (Inverse Document Frequency) Support:

Qdrant provides automatic IDF modification for sparse vectors:
- IDF depends on currently stored documents
- Cannot be pre-computed in streaming inference mode
- Qdrant modifies the sparse vector query with IDF statistics automatically
- Configurable via collection settings

### Sparse Index Configuration:
- Can be stored on-disk or in-memory
- On-disk is more compact but adds I/O overhead for cold queries
- Does NOT use HNSW - uses inverted-index-like data structure
- `enable_hnsw: false` can be set on payload indexes that are only used for sparse search filtering

**Source:** https://qdrant.tech/documentation/manage-data/vectors/#sparse-vectors
**Source:** https://qdrant.tech/documentation/manage-data/indexing/#sparse-vector-index

## 6. Fusion Method: How Dense + Sparse Search Are Combined

### Query API (v1.10.0+)

Qdrant provides a **universal Query API** with `prefetch` parameter for combining multiple searches. Hybrid search is implemented as multiple prefetches fused together.

### Fusion Methods:

#### 1. Reciprocal Rank Fusion (RRF) - Default

**Formula:**
```
score(d) = sum over rankings r_d in R(d) of: 1 / (k + r_d)
```

Where:
- `k` = constant (default: 2, configurable since v1.16.0)
- `r_d` = rank of document d in ranking r (zero-based)
- `R(d)` = set of rankings containing document d

**Weighted RRF (v1.17.0):**
```json
{
    "query": {
        "rrf": {
            "weights": [3.0, 1.0]
        }
    }
}
```
- Weights are applied per-prefetch in order
- A document ranked 3rd in a weight-3.0 prefetch scores same as rank 1 in weight-1.0

#### 2. Distribution-Based Score Fusion (DBSF) (v1.11.0)

**Formula:**
```
normalized_score = (score - (mean - 3*sigma)) / (6 * sigma)
```

- Computes mean and standard deviation from each prefetch's returned scores
- Normalizes scores to comparable ranges across retrievers
- Normalized scores are summed across retrievers
- **Not clipped to [0,1]** - outliers remain outside range
- Returns 0.5 for single-point or identical-score cases (avoids division by zero)
- **Stateless** - computes from current query results only

#### Choosing Between RRF and DBSF:

| Scenario | Recommended |
|----------|-------------|
| Eval set available for tuning | Weighted RRF (train/val split) |
| Trust raw scores, no eval set | DBSF |
| No eval set, no score priors | RRF (safe default) |
| Well-calibrated retrievers | DBSF may outperform tuned RRF |

### Multi-Stage Queries:

Beyond fusion, Qdrant supports **cascading searches**:
1. Fetch candidates with cheap representation (e.g., quantized vectors, short MRL vectors)
2. Re-score candidates with expensive representation (e.g., full-precision vectors, ColBERT multivectors)

Example: Fetch 1000 with byte vector, re-score top 100 with full vector, return top 10.

## 8. Known Issues with Filtered Search

### Issue 1: Recall Drop with Strict Filters
- **Root cause:** HNSW graph "falls apart" when filters are too strict
- **Evidence:** Qdrant's own documentation includes a chart showing precision drops as filter strictness increases
- **Mitigation:** Filterable HNSW (extra edges) helps, but extra edges are per-index, not per-combination
- **ACORN mitigation:** 2-hop exploration helps but at 2-10x performance cost

### Issue 2: Disconnected Graph Components
- **Root cause:** Combination of 2+ strict filters can create disconnected graph components
- **Root cause:** Large number of soft-deleted points
- **Mitigation:** ACORN algorithm (v1.16.0) - explores neighbors of neighbors
- **No automatic detection** - user must enable ACORN manually

### Issue 3: Payload Index Creation Timing
- **Issue:** Extra HNSW edges are only generated if payload indexes exist BEFORE data ingestion
- **Consequence:** Creating payload indexes after ingestion requires HNSW rebuild (resource-intensive)
- **Mitigation:** Always create payload indexes before ingesting data

### Issue 4: Memory Overhead of Extra Edges
- **Issue:** Each payload index adds extra edges to HNSW graph, increasing memory usage
- **Mitigation:** `enable_hnsw: false` (v1.17.0) to disable for fields not used in dense search
- **Tradeoff:** Disabling means those fields won't benefit from in-graph filtering

### Issue 5: Query Planning Heuristics
- **Issue:** Query planner uses heuristics that vary between Qdrant versions
- **Consequence:** Performance characteristics may change across upgrades
- **Mitigation:** Monitor and tune thresholds via configuration

### Issue 6: Batch Search Optimization Limitations
- **Issue:** Batch search optimization only works when requests share the same filter
- **Consequence:** Mixed-filter batches don't benefit from result sharing

### Issue 7: On-Disk Payload Index Latency
- **Issue:** On-disk payload indexes add disk I/O overhead for cold queries
- **Mitigation:** Keep hot payload indexes in memory; use on-disk only for rarely-used fields

### Issue 8: Sparse + Dense Hybrid Overhead
- **Issue:** When combining sparse and dense, each prefetch runs independently with its own limit
- **Consequence:** Prefetch limit must be >= main query limit + offset, or results may be empty
- **No automatic limit adjustment** - user must ensure limits are sufficient

### Issue 9: DBSF Score Instability
- **Issue:** DBSF normalization statistics come from small prefetch top-k samples
- **Consequence:** Single dominant outlier can skew normalization
- **Mitigation:** Increase prefetch `limit` for more stable rankings

## Summary: Key Vulnerabilities to Exploit

| Weakness | Opportunity |
|----------|-------------|
| Extra edges per-index, not per-combination | Combined strict filters still degrade |
| ACORN costs 2-10x performance | Can outperform on filtered search without ACORN |
| Payload indexes must be pre-created | Better dynamic index management |
| Query planner heuristics vary | More stable, predictable performance |
| DBSF normalization instability | More robust fusion methods |
| No filtered search benchmarks published | We can publish superior filtered search numbers |
| Memory overhead of extra edges | More memory-efficient filtered HNSW |
| Sparse index is always exact (no ANN) | Could use approximate sparse for better perf |
| Prefetch limits must be manually tuned | Auto-tuning would be a differentiator |
