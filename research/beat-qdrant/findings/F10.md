# F10: CUDA Graphs and GPU-Accelerated HNSW Graph Walks

## Research Focus
Can CUDA Graphs be used to accelerate HNSW graph walks in a vector database merge operation?

---

## 1. What Are CUDA Graphs?

CUDA Graphs represent a **fundamentally different execution model** from traditional CUDA streams. Instead of submitting kernel launches one-at-a-time (each paying host-side overhead), a CUDA Graph captures a **complete DAG (directed acyclic graph)** of operations — kernel launches, memory copies, memsets, host function calls, events, and conditionals — connected by explicit dependencies.

**Key insight from NVIDIA docs:** *"By creating a CUDA graph that encompasses a workflow that will be launched many times, these overhead costs can be paid once for the entire graph during instantiation, and the graph itself can then be launched repeatedly with very little overhead."*

### How Capture and Replay Works

There are two creation mechanisms:

#### A. Stream Capture (Recommended for Existing Code)
```cpp
cudaGraph_t graph;
cudaStreamBeginCapture(stream);
kernel_A<<< ..., stream >>>(...);
kernel_B<<< ..., stream >>>(...);
libraryCall(stream);
kernel_C<<< ..., stream >>>(...);
cudaStreamEndCapture(stream, &graph);
```
- Work is **not enqueued for execution** during capture
- Instead, work is **appended to an internal graph**
- Supports cross-stream dependencies via `cudaEventRecord`/`cudaStreamWaitEvent`
- Can capture existing library code without rewriting

#### B. Explicit Graph API
```cpp
cudaGraphCreate(&graph, 0);
cudaGraphAddNode(&nodes[0], graph, NULL, NULL, 0, &kParams);
cudaGraphAddNode(&nodes[1], graph, &nodes[0], NULL, 1, &kParams);
```
- Full control over topology and dependencies
- More verbose but more predictable

### Three-Phase Execution Model

1. **Definition/Creation**: Build graph description (stream capture or API)
2. **Instantiation**: `cudaGraphInstantiate()` — snapshots, validates, optimizes
3. **Execution**: `cudaGraphLaunch(graphExec, stream)` — minimal overhead

### Graph Node Types
- Kernel nodes
- CPU function call nodes
- Memory copy nodes (memcpy)
- Memset nodes
- Empty nodes
- Event wait/record nodes
- **Conditional nodes** (IF, WHILE, SWITCH) — added in CUDA 12.x
- Child graph nodes (nested graphs)

## 2. Can CUDA Graphs Handle Irregular/Variable-Length Graph Walks?

### The Challenge
HNSW graph walks are **inherently irregular**:
- Different queries take different numbers of hops
- Each hop may visit a different number of neighbors
- Work divergence is high across threads
- The graph topology changes during merge operations

### CUDA Graphs' Approach to Irregularity

**CUDA Graphs handle irregularity through conditional nodes (CUDA 12.x+):**

- **WHILE nodes**: Execute body graph repeatedly while condition is true
- **IF nodes**: Conditional execution with optional else branch
- **SWITCH nodes**: Select which sub-graph to execute based on a value

```cpp
// WHILE loop example from NVIDIA docs
cudaGraphConditionalHandle handle;
cudaGraphConditionalHandleCreate(&handle, graph, 1, cudaGraphCondAssignDefault);

// Create WHILE conditional node
cudaGraphNodeParams cParams = { cudaGraphNodeTypeConditional };
cParams.conditional.handle = handle;
cParams.conditional.type   = cudaGraphCondTypeWhile;
cParams.conditional.size   = 1;
cudaGraphAddNode(&node, graph, NULL, 0, &cParams);

// Inside body: kernel sets handle to 0 when done
__global__ void loopKernel(cudaGraphConditionalHandle handle, char *dPtr) {
    if (--(*dPtr) == 0) {
        cudaGraphSetConditional(handle, 0);  // Exit loop
    }
}
```

**Key insight**: The condition is evaluated **on the device** when dependencies are met, enabling data-dependent control flow entirely on GPU.

### Assessment for HNSW Walks

**Partial fit**: CUDA Graphs CAN model iterative graph traversal via WHILE conditionals, but with significant caveats:

| Aspect | CUDA Graphs | HNSW Walk Need |
|--------|-------------|----------------|
| Fixed iteration count | YES (known at instantiation) | NO (variable per query) |
| Data-dependent branching | YES (conditional nodes) | YES |
| Variable work per iteration | YES (graph nodes can have different grid sizes) | YES |
| Dynamic topology changes | NO (graph structure fixed at instantiation) | YES (during merge) |
| Dynamic memory allocation | LIMITED (memory pools only) | YES (frontier expansion) |

**Verdict**: CUDA Graphs can model the **search/traversal** pattern (fixed topology, variable iterations), but NOT the **merge/insertion** pattern (dynamic topology changes).

## 3. How Do CUDA Graphs Handle Loops with Variable Iteration Counts?

### Conditional WHILE Nodes (CUDA 12.4+)

The WHILE node is the primary mechanism:

1. A **conditional handle** holds a device-side value
2. The handle is initialized (default value at launch or set by upstream kernel)
3. The body graph executes
4. After body completion, the condition is re-evaluated
5. Loop continues while condition != 0

```cpp
// Variable iteration: upstream kernel sets iteration count
__global__ void setLoopCount(cudaGraphConditionalHandle handle, int* count) {
    cudaGraphSetConditional(handle, *count);  // Set from device memory
}
```

### Key Limitations for Variable Iterations

1. **The graph topology is fixed at instantiation** — you cannot add/remove nodes dynamically
2. **All threads in a WHILE node share the same condition** — no per-thread loop counts
3. **Work divergence**: If different threads need different iteration counts, you need a max-iteration design with conditional early exit inside the kernel
4. **No dynamic memory**: Cannot allocate new memory during loop iterations

### Practical Pattern for Variable-Length Walks

```cpp
// Batch of walks with different lengths — pad to max, use early exit
__global__ void graphWalkKernel(
    int* visited, int* frontier, int* next_frontier,
    int* walk_lengths,  // Per-query walk lengths
    int max_iterations,
    cudaGraphConditionalHandle handle
) {
    // Each thread handles one query
    int tid = threadIdx.x + blockIdx.x * blockDim.x;
    if (tid < n_queries && walk_lengths[tid] > current_iteration) {
        // Do one hop of the walk
        // ...
    }
    // After all iterations done, set handle to 0
    if (current_iteration >= max_iterations) {
        cudaGraphSetConditional(handle, 0);
    }
}
```

**The WHILE loop runs for max(all walk lengths), with early exit per thread inside the kernel.** This is the standard GPU approach for variable-length computations.

## 4. Overhead: CUDA Graph Launch vs Individual Kernels

### Measured Overhead Characteristics

| Operation | Typical Overhead |
|-----------|-----------------|
| Individual kernel launch | **5-10 microseconds** per launch (host-side) |
| CUDA Graph instantiation | **One-time cost** (comparable to ~10-100 kernel launches) |
| CUDA Graph launch | **~2-5 microseconds** (near zero CPU overhead after instantiation) |
| Graph update (parameters only) | **<1 microsecond** (no re-instantiation) |

### Why Graphs Are Faster for Repeated Workloads

From NVIDIA docs: *"For a GPU kernel with a short execution time, this overhead cost [of individual launches] can be a significant fraction of the overall end-to-end execution time."*

**The optimization**: Graph instantiation performs:
- One-time validation of all dependencies
- Pre-computation of launch metadata
- CUDA driver optimization of the execution plan
- Memory handle pinning

**For HNSW graph walks**: If each hop is a short kernel (e.g., neighbor distance computation + priority queue update), the per-launch overhead of 5-10us can dominate. A CUDA Graph that captures the entire iterative walk can eliminate this overhead entirely.

### Quantified Benefits

For a workflow with N kernel launches:
- **Without graphs**: N × ~7us overhead = **N × 7us**
- **With graphs**: ~3us total overhead, regardless of N
- **For 20 iterations × 4 kernels/iteration**: 80 × 7us = 560us vs 3us = **~187x reduction in launch overhead**

## 5. Can CUDA Graphs Be Used for BFS/DFS Graph Traversal?

### BFS on GPU with CUDA Graphs

**Yes, but with important caveats:**

#### cuGraph BFS Implementation
cuGraph (RAPIDS) provides GPU-accelerated BFS:
- Multi-GPU support via cuDF integration
- Uses frontier-based parallel BFS
- Single-source and batched multi-source BFS
- Cutoff distance support

#### CUDA Graph + BFS Pattern

```cpp
// BFS as CUDA Graph with WHILE conditional
cudaGraph_t graph;
cudaStreamBeginCapture(stream);

// Setup
cudaMemsetAsync(frontier, 0, ...);
setStartNode<<<1,1>>>(frontier, start_node);
setLoopCount<<<1,1>>>(handle, &depth_limit);

// WHILE loop body
cudaGraph_t bodyGraph;
// kernel: expand frontier
expandFrontier<<<gridSize, blockSize>>>(adjacency, frontier, next_frontier, visited, handle);
// kernel: swap frontiers
swapBuffers<<<1,1>>>(frontier, next_frontier, handle);

cudaStreamEndCapture(stream, &graph);
```

**Limitations for BFS:**
1. **Frontier size is dynamic** — cannot resize arrays within the graph
2. **Work-per-iteration varies wildly** — early levels process few nodes, middle levels process many
3. **Memory allocation during traversal** — not supported in graph nodes

### DFS on GPU with CUDA Graphs

**DFS is poorly suited for GPU execution** in general:
- Inherently sequential (stack-based)
- Poor memory access patterns (random jumps)
- Limited parallelism

**CUDA Graphs don't help** — the fundamental issue is the algorithm, not the launch overhead.

### Better Alternative: Level-Synchronous BFS

For HNSW-style multi-level graph traversal:
```cpp
// Level 0: coarse graph (HNSW upper levels)
// Each level = one kernel launch or one graph node
// CUDA Graph captures the full multi-level traversal

for (int level = max_level; level >= 0; level--) {
    searchAtLevel<<<...>>>(queries, graph_levels[level], current_candidates);
}
// All levels captured as a single graph
```

## 6. GPU-Accelerated HNSW Graph Construction: Papers and Implementations

### Key Papers

#### CAGRA (ICDE 2024)
**"CAGRA: Highly Parallel Graph Construction and Approximate Nearest Neighbor Search for GPUs"**
- Authors: Ootomo, Naruse, Nolet, Wang, Feher, Wang
- arXiv: 2308.15136
- **Key results:**
  - Graph construction: **2.2-27x faster** than CPU HNSW
  - Large-batch query throughput at 90-95% recall: **33-77x faster** than CPU HNSW
  - Single query at 95% recall: **3.4-53x faster** than CPU HNSW
  - Surpasses existing GPU-based methods by **3.8-8.8x** at high recall
- **Approach**: Builds kNN graph first, then prunes redundant paths (NSG-style)
- **Not HNSW**: Uses flat graph representation, not hierarchical

#### GPU-HNSW (NC State SASER Lab)
- Research project on GPU-accelerated HNSW
- Challenges: Irregular memory access, variable degree per node
- Key finding: GPU benefits diminish for small datasets (<1M vectors)

#### "Efficient Large-scale Approximate Nearest Neighbor Search on the GPU" (Wieschollek et al., CVPR 2016)
- Early GPU ANN search work
- Focuses on IVF-based approaches, not graph-based

### Production Implementations

## 7. cuGraph: NVIDIA's GPU Graph Analytics Library

### What cuGraph Provides

cuGraph is part of the RAPIDS ecosystem and provides GPU-accelerated implementations of common graph algorithms:

#### Traversal Algorithms
- **BFS** (Breadth-First Search) — Multi-GPU support, with cutoff
- **SSSP** (Single-Source Shortest Path) — Multi-GPU support

#### Centrality Algorithms
- Betweenness Centrality (Multi-GPU)
- PageRank (Multi-GPU, including personalized)
- Katz Centrality
- Eigenvector Centrality
- Degree Centrality

#### Community Detection
- Louvain (Multi-GPU)
- Leiden (Multi-GPU)
- Triangle Counting (Multi-GPU)
- K-Core (Multi-GPU)

#### Link Prediction
- Jaccard Similarity (Multi-GPU)
- Overlap Similarity
- Cosine Similarity

#### Sampling
- Random Walks (Multi-GPU)
- Node2Vec (Multi-GPU)
- Neighborhood Sampling

### How cuGraph Handles Graph Algorithms

cuGraph uses **CSR (Compressed Sparse Row)** format for graph storage:
- Edges stored in GPU memory as contiguous arrays
- Adjacency information via offset array
- Enables coalesced memory access for frontier expansion

**Key implementation details:**
- Level-synchronous BFS with frontier tracking
- Work-efficient parallel prefix sum for frontier management
- Multi-GPU via graph partitioning across GPUs
- Integration with cuDF DataFrames for I/O

### Relevance to HNSW

cuGraph's BFS/SSSP could theoretically traverse HNSW graphs on GPU, but:
1. **HNSW graphs are small-world** — BFS is efficient
2. **HNSW requires priority-queue-based greedy search** — not standard BFS
3. **No native HNSW data structure support** — would need custom implementation

## 8. Batching Multiple Graph Walks into a Single CUDA Graph

### Yes, This Is the Primary Use Case for CUDA Graphs

**The batching pattern:**

```cpp
// N queries, each performing M iterations of graph walk
// Captured as ONE graph with M kernel launches

cudaStreamBeginCapture(stream);

for (int i = 0; i < M; i++) {
    // Each kernel handles ALL N queries in parallel
    graphWalkStep<<<(N+255)/256, 256>>>(
        queries, adjacency, distances, visited,
        frontier_sizes, next_frontier_sizes, i
    );
}

cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);

// Launch once, all N queries processed
cudaGraphLaunch(graphExec, stream);
```

### Benefits of This Approach

1. **Eliminates per-iteration launch overhead**: Instead of M kernel launches, one graph launch
2. **Enables cross-iteration optimizations**: CUDA can reorder, merge, or overlap operations
3. **Reduces CPU involvement**: After instantiation, CPU is free for other work
4. **Better GPU utilization**: Graph scheduler can overlap compute and memory operations across iterations

### Advanced: Multi-Stage Pipeline Graph

```cpp
// Pipeline: distance computation -> sort -> update frontier
cudaGraph_t graph;
cudaStreamBeginCapture(stream);

// Stage 1: Compute distances to neighbors
computeDistances<<<grid, block>>>(...);

// Stage 2: Sort and select top-K candidates
selectTopK<<<grid, block>>>(...);

// Stage 3: Update visited set and frontier
updateFrontier<<<grid, block>>>(...);

cudaStreamEndCapture(stream, &graph);
// All three stages captured as a single graph
// Can be replayed M times for M iterations
```

### Limitations for Dynamic Batching

| Scenario | CUDA Graphs Support |
|----------|-------------------|
| Fixed batch size N | YES |
| Fixed iteration count M | YES (with WHILE conditional) |
| Dynamic batch size (queries arrive over time) | NO — must rebuild graph |
| Dynamic graph topology (merge operations) | NO — structure fixed at instantiation |
| Dynamic memory allocation during walks | NO — only pre-allocated pools |

## 9. Limitations of CUDA Graphs

### Critical Limitations for HNSW Merge

#### A. No Dynamic Graph Topology
**This is the fatal limitation for HNSW merge operations.**
- HNSW merge involves adding nodes and edges to the graph
- CUDA Graph structure is fixed at instantiation
- Cannot add new kernel nodes or change dependency edges
- **Workaround**: Re-instantiate graph after each batch of insertions (expensive)

#### B. No Dynamic Memory Allocation
- Cannot call `cudaMalloc` inside a graph node
- Must pre-allocate all memory at graph creation
- Memory pools (CUDA 12.x stream-ordered allocator) can help but are limited
- **Impact**: Cannot grow frontier arrays during BFS walks

#### C. Fixed Grid/Block Dimensions
- Kernel launch configurations are fixed at instantiation
- Cannot change grid size between iterations
- **Workaround**: Use maximum expected size and mask inactive threads

#### D. No Synchronous Operations
- Cannot synchronize device within a graph
- Cannot query device state
- Must use events or device-side conditionals

#### E. Limited Conditional Node Support (CUDA 12.4+)
- WHILE nodes run same body graph for all threads
- No per-thread conditional execution
- Switch nodes limited to discrete cases

#### F. Update Limitations
- Cannot change kernel function pointer (must use same kernel)
- Cannot change memory allocation context
- Cannot change memcpy source/destination types
- Node enable/disable is the only structural change

### Summary of Limitations

| Limitation | Impact on HNSW Merge | Severity |
|-----------|---------------------|----------|
| Fixed graph topology | Cannot add new nodes/edges | **CRITICAL** |
| No dynamic memory | Cannot grow data structures | **HIGH** |
| Fixed grid dimensions | Cannot adapt to changing work | **MEDIUM** |
| No per-thread control flow | All threads share loop condition | **MEDIUM** |
| Re-instantiation cost | Must rebuild for topology changes | **HIGH** |

## 10. GPU-Native HNSW Implementation (FAISS GpuIndex, cuVS CAGRA)

### FAISS GPU Indexes

FAISS provides GPU implementations for:
- **GpuIndexFlat** — brute-force GPU search
- **GpuIndexIVFFlat** — IVF with flat storage
- **GpuIndexIVFScalarQuantizer** — IVF with scalar quantization
- **GpuIndexIVFPQ** — IVF with product quantization

**CRITICAL: FAISS does NOT have a GPU HNSW index.**
- HNSW is CPU-only in FAISS
- GPU acceleration is only for IVF and flat indexes
- Performance: GPU FAISS is 5-10x faster than CPU for supported indexes

### cuVS CAGRA — The GPU-Native Graph Index

**CAGRA (CUDA ANN Graph)** is the closest thing to GPU-native HNSW:

#### Architecture
1. **Build Phase**:
   - Construct kNN graph using IVF-PQ or NN-Descent on GPU
   - Prune redundant routes (NSG-style)
   - Result: Flat graph representation (not hierarchical like HNSW)

2. **Search Phase**:
   - GPU-parallelized greedy graph search
   - Batched multi-query support
   - Priority queue management in shared memory

#### CAGRA vs HNSW Comparison

| Aspect | HNSW (CPU) | CAGRA (GPU) |
|--------|-----------|-------------|
| Graph structure | Hierarchical (multi-level) | Flat (single level) |
| Build time | Sequential (slow) | Parallel (fast) |
| Search latency | Good | Better (GPU parallelism) |
| Throughput | Moderate | Very high |
| Memory efficiency | Good (hierarchical skips) | Moderate (flat graph) |
| Update support | Incremental (add nodes) | Full rebuild |
| Recall at 95% | ~95% | ~93-96% |

#### cuVS Integration with FAISS

FAISS can now use cuVS as a backend:
```python
# Build CAGRA index via cuVS
index_params = cagra.IndexParams()
index = cagra.build(index_params, dataset)

# Serialize to CPU HNSW for deployment
# (cuVS builds faster, HNSW is more memory-efficient)
```

### Other GPU ANN Systems

| System | Algorithm | GPU Support |
|--------|----------|-------------|
| NVIDIA cuVS | CAGRA, IVF-PQ, NN-Descent | Full GPU |
| FAISS | IVF, Flat, PQ | GPU for IVF/Flat |
| ScaNN (Google) | IVF + ANNS | TPU optimized |
| DiskANN (Microsoft) | Graph-based | CPU + SSD |
| Milvus | Multiple | GPU via IVF |

## Synthesis: CUDA Graphs for HNSW Merge — Feasibility Assessment

### What CUDA Graphs CAN Accelerate

1. **HNSW Search (Greedy Graph Walk)**
   - Batch multiple queries into single graph launch
   - WHILE conditional for variable-depth traversal
   - Eliminates per-iteration launch overhead
   - **Expected speedup: 2-5x** over individual kernel launches

2. **HNSW Build (kNN Graph Construction)**
   - Parallel kNN computation captured as graph
   - Fixed-iteration NN-Descent as WHILE loop
   - **Expected speedup: 3-10x** over sequential kernel launches

3. **Level-Synchronous Traversal**
   - Multi-level HNSW traversal as sequential graph nodes
   - Each level = one kernel node
   - Dependencies ensure correct ordering

### What CUDA Graphs CANNOT Accelerate

1. **Incremental HNSW Merge**
   - Cannot add nodes/edges to graph after instantiation
   - Must re-instantiate for each batch of insertions
   - Re-instantiation cost negates launch savings

2. **Dynamic Topology Changes**
   - Graph structure is immutable after instantiation
   - HNSW merge requires dynamic edge updates

3. **Memory-Growing Operations**
   - Cannot allocate new memory during graph execution
   - HNSW frontier arrays may grow during search

### Recommended Architecture

```
┌─────────────────────────────────────────────────────┐
│              HNSW Merge Pipeline                      │
├─────────────────────────────────────────────────────┤
│                                                       │
│  Phase 1: Batch Insert (CPU-driven)                   │
│  ├── Collect N vectors to insert                      │
│  ├── CPU manages HNSW graph structure                 │
│  └── GPU handles distance computations                │
│                                                       │
│  Phase 2: Parallel kNN Search (GPU Graph)             │
│  ├── CUDA Graph captures batch search                 │
│  ├── WHILE conditional for variable iterations        │
│  ├── N queries processed in parallel                  │
│  └── Results used to update graph edges               │
│                                                       │
│  Phase 3: Edge Pruning (GPU Kernel)                   │
│  ├── Standard GPU kernel for NSG-style pruning        │
│  └── Not suitable for CUDA Graph (one-shot)           │
│                                                       │
└─────────────────────────────────────────────────────┘
```

### Alternative: Use cuVS CAGRA Instead of HNSW

**If GPU acceleration is the priority:**
1. Use CAGRA for graph construction (2-27x faster than CPU HNSW build)
2. Use CAGRA for search (33-77x faster than CPU HNSW)
3. Serialize to CPU HNSW for production deployment
4. **Skip CUDA Graphs entirely** — CAGRA handles the parallelism internally

### Final Recommendation

| Goal | Recommendation |
|------|---------------|
| Accelerate HNSW search on GPU | CUDA Graphs + WHILE conditional (moderate benefit) |
| Accelerate HNSW build on GPU | Use CAGRA instead (major benefit) |
| Accelerate HNSW merge on GPU | Not feasible with CUDA Graphs — use batch CPU merge with GPU kNN |
| Production GPU ANNS | Use cuVS CAGRA (state-of-the-art) |
| Hybrid CPU/GPU approach | GPU for kNN construction, CPU for HNSW topology management |
