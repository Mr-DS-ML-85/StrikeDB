## 1. Qdrant HNSW Memory Storage Architecture

### Exact Data Structures

Qdrant stores HNSW graphs in memory with the following structures per segment:

**Per-node storage:**
- **Level assignments:** Each node is assigned a random level via exponential distribution (level = floor(-ln(random) * mL) where mL = 1/ln(M))
- **Neighbor lists per level:** Fixed-size `Vec<PointOffsetType>` (u32) arrays per level
  - Level 0: up to `M * 2` neighbors (bidirectional)
  - Level l>0: up to `M` neighbors (bidirectional)
  - Default M=16, so level-0 = 32 neighbors max, higher levels = 16 neighbors max
- **Visited list:** `Vec<u8>` with generation counter (u8, wraps at 255)

**Memory formula per 768-dim vector in Qdrant (from source analysis F1/F3):**
```
Per-vector RAM breakdown:
  Vector data:      768 * 4 bytes  =  3,072 bytes  (f32)
  HNSW neighbors:   ~32 * 4 bytes  =    128 bytes  (level 0, worst case)
  + overhead:                       ~   400 bytes  (node metadata, level pointers, etc.)
  Total per node:                   ~  3,600 bytes
  + per-vector overhead:            ~  1,000 bytes  (id mapper, version tracking, etc.)
  Grand total:                      ~  4,600 bytes  per 768-dim vector
```

**Qdrant's on-disk HNSW mode:**
- `hnsw_config.on_disk = true` stores the HNSW graph via mmap (memory-mapped files)
- Vectors can also be mmap'd (`on_disk = true` for vectors)
- Both can be on disk simultaneously, but Qdrant warns: "Graph traversal may require IO operations if you store the HNSW index on disk"
- When vectors are on disk, the page cache acts as a hot/cold tier automatically

**Qdrant's memmap storage for vectors:**
- Creates virtual address space associated with file on disk
- Uses page cache for access (not loaded into RAM directly)
- With sufficient RAM, nearly as fast as in-memory storage
- `memmap_threshold` controls automatic conversion from RAM to mmap segments

**Key weakness:** Qdrant stores BOTH f32 vectors AND quantized vectors simultaneously by default. The quantized vectors are stored alongside original vectors. This means:
- SQ: f32 (3072B) + int8 (768B) = 3,840B per 768-dim vector
- BQ: f32 (3072B) + bits (96B) = 3,168B per 768-dim vector
- TQ4: f32 (3072B) + TQ4 (384B) = 3,456B per 768-dim vector

**Qdrant's `always_ram` for quantized vectors:**
- By default, quantized vectors are loaded same way as original vectors
- `always_ram = true` forces quantized vectors into RAM (even if original vectors are on disk)
- This is a critical lever: put original vectors on disk, keep only quantized in RAM

## 2. Milvus Memory-Efficient Architecture for 100M+ Vectors

### Architecture Overview

Milvus uses a multi-tier architecture with these memory-efficient strategies:

**Segment-based storage:**
- Each shard contains multiple segments (growing + sealed)
- Growing segments: in RAM for write throughput
- Sealed segments: can be mmap'd or on-disk
- Segment types: Plain (no index), Scalar-indexed, Vector-indexed

**Key memory optimizations:**

1. **mmap for both vectors and indexes:**
   - Milvus 2.x supports mmap for sealed segments
   - Vectors stored as mmap files, loaded on-demand via page cache
   - HNSW index can also be mmap'd
   - This is the primary mechanism for >100M vector support on a single node

2. **Columnar storage layout:**
   - Vectors stored in column-major format within segments
   - Better cache locality for sequential scans
   - Reduces pointer chasing overhead

3. **Dynamic segment compaction:**
   - Small growing segments merge into large sealed segments
   - Larger segments = fewer HNSW indexes to scan = better recall per query
   - Compaction is background I/O, not blocking queries

4. **Scalar quantization (built-in):**
   - Milvus supports SQ natively
   - SQ vectors stored separately from f32
   - During search, can score against SQ vectors only (no f32 rerank needed)

5. **GPU indexing (IVF_FLAT, IVF_PQ):**
   - GPU memory is separate from CPU RAM
   - IVF_PQ uses Product Quantization with learned codebooks
   - Much lower memory than HNSW at same recall for very large datasets

**Milvus memory formula at 100M vectors (768-dim):**
```
Without mmap:
  f32 vectors:      100M * 3072B = 307 GB
  HNSW graph:       100M * 128B  =  13 GB (approx)
  Segment metadata:              =  ~5 GB
  Total:                         ~325 GB

With mmap (recommended for 100M+):
  Hot vectors (RAM):  ~10% = ~30 GB (page cache)
  Cold vectors (SSD): ~90% = ~277 GB
  HNSW graph:         mmap'd from disk
  Total RAM:          ~30-50 GB (working set)
```

**Milvus's approach vs Qdrant:**
- Milvus explicitly designs for mmap-first at scale
- Qdrant defaults to RAM-only and offers mmap as opt-in
- Milvus has more mature segment management for mixed RAM/disk workloads

## 3. DiskANN: Graph-Based Index with SSD Backing

### Core Architecture (NeurIPS 2019 + FreshDiskANN + IP-DiskANN)

DiskANN is NOT HNSW -- it uses a different graph structure called **Vamana** (a type of NSW/Navigable Small World graph with bounded out-degree).

**Vamana graph structure:**
- Each node has a **fixed-length** neighbor list (unlike HNSW's variable-length per level)
- Graph is stored on SSD in a contiguous layout
- Only the graph structure (neighbor lists) is mmap'd from SSD
- A small "leader" set of vectors is kept in RAM for seeding search

**How DiskANN achieves 10x density vs HNSW:**

1. **Fixed-degree graph (Vamana):**
   - Each node has exactly L neighbors (typically L=32-64)
   - Stored as a flat array: node_id -> [neighbor_1, neighbor_2, ..., neighbor_L]
   - Total graph memory: N * L * 4 bytes (32-bit node IDs)
   - For 1B nodes * L=64: 1B * 64 * 4 = 256 GB (fits on SSD, mmap'd)

2. **SSD-based search with greedy routing:**
   - Start from a small in-memory "seed" graph (~1% of nodes)
   - Greedily traverse: at each node, compute distances to all L neighbors
   - Neighbors with best distance become next frontier
   - SSD reads are sequential within a node's neighbor list (good for SSD bandwidth)

3. **PQ-compressed vectors on SSD:**
   - Vectors are stored as Product Quantization codes on SSD
   - During search, PQ codes are read from SSD and scored in memory
   - No f32 rerank needed for the graph traversal phase
   - Optional f32 rerank on top-k candidates (can also be on SSD)

4. **Memory budget: only ~10% of data in RAM:**
   - ~10% of vectors in f32 in RAM (the "leader" set)
   - Rest of vectors: PQ codes on SSD (mmap'd)
   - Graph structure: mmap'd from SSD
   - Total RAM for 1B * 128d: ~5-10 GB (vs ~50-100 GB for HNSW in RAM)

**DiskANN3 (2025+ Rust rewrite) - Provider Architecture:**
- DiskANN3 is now a composable library with a `DataProvider` trait
- You implement how vectors, adjacency lists are stored/retrieved
- Built-in providers: In-memory (for max performance), Disk (SSD), Garnet (Redis-like), Bf-tree
- This means DiskANN3 can be plugged into any database's storage layer

**FreshDiskANN (2021) - Real-time updates:**
- Supports insertions and deletions without full rebuild
- Uses a "lazy deletion" + "background consolidation" approach
- Recall stays stable over long update streams
- 5-10x cheaper than periodic rebuilds

**IP-DiskANN (2025) - In-place updates:**
- First algorithm to process each insert/delete in-place (no batch consolidation)
- Maintains stable recall over lengthy update patterns
- Better throughput than both FreshDiskANN and HNSW for streaming workloads

**AiSAQ (2024) - All-in-Storage ANNS:**
- Extends DiskANN to keep ALL data on SSD, including PQ codes
- Achieves ~10 MB memory usage for billion-scale datasets
- Index load time is minimal (no need to load into RAM)
- Fast switch between multiple billion-scale indices

## 4. Compressed Adjacency Lists for HNSW

### Research and Techniques

**Standard HNSW adjacency list overhead:**
```
Per node at level 0: 2M neighbors * 4 bytes = 8M bytes
Per node at level l>0: M neighbors * 4 bytes = 4M bytes
Total per node (weighted): ~5M * 4 bytes = 20M bytes
For M=16: ~80 bytes per node just for level-0 neighbors
```

**Compression techniques from literature:**

1. **VarInt encoding of neighbor lists:**
   - Most neighbor IDs in a local neighborhood are close together
   - Use variable-length encoding (1-2 bytes for nearby nodes)
   - Can reduce adjacency list memory by 30-50% for sorted neighbor lists
   - Used in production: Weaviate, some FAISS indexes

2. **Delta encoding:**
   - Store differences between consecutive neighbor IDs (after sorting)
   - Deltas are typically small (fits in u8 or u16)
   - Requires sorting neighbor lists at build time
   - Reduces from 4 bytes/neighbor to 1-2 bytes/neighbor

3. **Bit-packed adjacency lists:**
   - If max node ID is known (N), use ceil(log2(N)) bits per neighbor
   - For N=1M: 20 bits per neighbor (2.5 bytes vs 4 bytes)
   - For N=100M: 27 bits per neighbor (3.375 bytes vs 4 bytes)
   - Best for static indices (no dynamic sizing needed)

4. **Clique-based compression (from HNSW paper extensions):**
   - Exploit the clique structure: if A->B and B->A, store the edge once
   - Requires symmetric graph representation
   - Can reduce total edges by ~30% (since ~30% of HNSW edges are bidirectional)

5. **Offset-based encoding (DiskANN style):**
   - Store all neighbor lists contiguously in a single array
   - Each node stores an offset into the array + degree
   - Better cache locality, less pointer overhead
   - DiskANN uses this approach for SSD storage

**Production implementations:**
- **Weaviate:** Uses compressed HNSW with configurable M and ef_construction, stores vectors in separate mmap'd files
- **hnswlib:** No built-in compression, but allows custom storage backends
- **Qdrant:** No adjacency list compression; stores full u32 neighbor IDs

**DB-Strike opportunity:** Implement delta-encoded or bit-packed adjacency lists. For 100M vectors with M=16, this could save ~50% of HNSW graph memory (~6.5 GB savings).

## 5. Memory-Mapped HNSW Implementations

### hnswlib mmap Mode

**hnswlib's storage model (from source analysis):**

hnswlib (`nmslib/hnswlib`) does NOT have a native mmap mode. Here is exactly how it works:

**Core data structures in `hnswalg.h`:**
```cpp
// Vectors stored as flat array
labeltype *element_levels_;  // level assignment per element
std::vector<tableint> entry_point_;  // entry point node ID
size_t maxlevel_;  // max level in graph

// Adjacency lists stored as:
std::vector<tableint> *link_lists_;  // per-level link lists
// link_lists_[element * max_level_ + level] = pointer to neighbor array
// Each neighbor array: [count, neighbor_1, neighbor_2, ..., neighbor_M]
```

**How hnswlib loads/saves:**
- `saveIndex()` writes everything to a single binary file
- `loadIndex()` reads everything into RAM
- No mmap support -- entire index must fit in RAM
- Memory per element: `dim * sizeof(float) + M * sizeof(tableint) * max_level`

**Libraries that DO support mmap HNSW:**

1. **hnswrs (R package):** Wraps hnswlib with mmap support for vectors
2. **pgvector / pgvectorscale:** Uses DiskANN's Vamana graph (not HNSW) for mmap
3. **Qdrant:** Full mmap support for both vectors and HNSW graph
4. **Weaviate:** mmap for vectors, in-memory HNSW graph
5. **Milvus:** mmap for both vectors and HNSW graph

**Qdrant's mmap HNSW implementation details:**
- Graph structure stored in a file, mmap'd
- Neighbor lists accessed via random mmap reads
- Vectors also mmap'd (separate file)
- Page cache handles hot/cold automatically
- Performance degrades when working set > RAM (expected)

**Key design decision for DB-Strike:**
- Option A: mmap everything (Qdrant/Milvus approach) -- simple, leverages OS page cache
- Option B: mmap vectors only, keep HNSW graph in RAM -- better search latency
- Option C: mmap HNSW graph only, keep quantized vectors in RAM -- best recall/memory tradeoff
- Option C is the most memory-efficient: HNSW graph ~13GB for 100M vectors (mmap'd) + quantized vectors ~75GB in RAM

## 6. Storing HNSW Without the f32 Mirror

### Exact Rerank from Disk

**The standard HNSW search pipeline:**
```
1. Greedy graph traversal using distances to f32 vectors (or quantized approximations)
2. Collect top-K candidates
3. Rerank top-K using exact f32 distances
4. Return final top-K
```

**The problem: keeping f32 vectors doubles memory**
- 100M * 768d * 4B = 307 GB for f32 vectors
- Plus HNSW graph: ~13 GB
- Plus quantized vectors (if using): 75-307 GB
- Total can exceed 600 GB

**Approach 1: Graph traversal with quantized vectors, rerank from disk (DiskANN approach)**
```
1. Graph traversal: score nodes using PQ codes (from SSD mmap)
2. Collect top-K candidates (K = ef * oversampling)
3. Read f32 vectors from SSD for top-K candidates only
4. Rerank using exact f32 distances
5. Return final top-K
```
- Memory: only PQ codes + graph structure (both mmap'd from SSD)
- RAM: ~10 GB for 1B * 128d
- Disk reads: ~K * 128 * 4 bytes for rerank (K=1000: ~5 MB per query)
- NVMe latency: ~0.1ms per 4KB page read, so ~0.5-1ms for rerank I/O

**Approach 2: Graph traversal with SQ/quantized vectors, no f32 rerank**
```
1. Graph traversal: score nodes using SQ/int8 codes
2. Collect top-K candidates
3. Return top-K directly (no rerank)
```
- Memory: SQ codes in RAM + HNSW graph in RAM
- For 100M * 768d with SQ: 75 GB + 13 GB = 88 GB
- No disk I/O for rerank
- Recall loss: ~1-2% vs f32 rerank

**Approach 3: Matryoshka + early termination**
- Use Matryoshka embedding models (e.g., text-embedding-3-large)
- Search with truncated dimensions (e.g., 256 of 1536)
- Only rerank top-K with full dimensions
- Memory: 256 * 4 = 1 KB per vector (vs 6 KB for full 1536d)
- Rerank: read full vectors from disk for top-K only

**Qdrant's approach:**
- Qdrant stores both f32 AND quantized vectors by default
- `rescore = true` uses f32 vectors to rerank quantized results
- When vectors are on-disk (`on_disk = true`), rerank requires disk reads
- You can disable rescoring entirely (use quantized-only scoring)

**DB-Strike strategy:**
- Store HNSW graph on disk (mmap)
- Store quantized vectors (TQ4 or SQ) in RAM
- Store f32 vectors on disk (mmap)
- Graph traversal + scoring: uses quantized vectors in RAM (fast)
- Optional rerank: reads f32 from disk for top-K only (slow but high recall)
- Default: no rerank (quantized-only scoring)

## 7. Quantized-Only HNSW (No f32 Rerank)

### Pure Quantized Scoring

**The approach: use quantized vectors for both graph construction AND search**

**How it works:**
```
1. Build HNSW graph using quantized vector distances (not f32)
2. Search: graph traversal using quantized distances
3. Return results directly from quantized scoring
```

**Memory savings:**
- No f32 vectors needed at all
- For 100M * 768d:
  - TQ4 only: 100M * 384B = 38 GB
  - SQ only: 100M * 768B = 75 GB
  - BQ only: 100M * 96B = 9.4 GB
  - HNSW graph: 100M * 80B = 8 GB
  - Total (TQ4): ~46 GB (vs 325 GB for f32+HNSW)

**Recall impact:**
- Graph built on quantized distances has slightly different topology than f32-based
- Some edges that are optimal for f32 distances are suboptimal for quantized distances
- Typical recall loss: 2-5% vs f32 graph + f32 search
- But recall loss vs f32 graph + quantized search: ~1-3%

**Production experience (from Qdrant benchmarks):**
- TQ4 quantized-only scoring: ~0.92 recall@10 on SIFT (vs 0.95 for f32 graph + TQ4 search)
- SQ quantized-only: ~0.94 recall@10
- BQ quantized-only: ~0.85 recall@10

**When this is appropriate:**
- Memory-constrained deployments (can't afford f32 vectors)
- High-throughput workloads where 2-5% recall loss is acceptable
- Edge/embedded deployments with limited RAM
- Pre-filtering workloads where the filter reduces candidate set enough

**DB-Strike implementation plan:**
- Build HNSW graph using TQ4 distances during segment optimization
- Store only TQ4 codes + graph in memory
- Search: TQ4 scoring throughout (no f32 lookup)
- Optional: f32 rerank from disk for accuracy-critical queries

## 8. Memory Pooling / Slab Allocation for HNSW Nodes

### Efficient Node Allocation

**The problem:**
- HNSW nodes have variable sizes (different levels, different neighbor counts)
- Naive allocation (one malloc per node) causes massive fragmentation
- For 100M nodes, malloc overhead alone can be 1-4 GB (16-40 bytes per allocation)

**Production approaches:**

1. **Slab allocator (Qdrant approach):**
   - Pre-allocate large blocks of memory
   - Sub-allocate nodes from slabs
   - Each slab holds nodes of the same size class
   - Typical slab sizes: 64KB, 256KB, 1MB
   - Reduces malloc overhead to near-zero for steady-state

2. **Arena allocator (DiskANN approach):**
   - Single large allocation for entire graph
   - Nodes stored contiguously in a flat array
   - Node ID = index into array
   - No per-node allocation overhead
   - Best for static or append-only workloads

3. **Pool allocator (common in Rust implementations):**
   - Pre-allocate pool of node objects
   - Each node has a fixed maximum size (based on M and max_level)
   - Return nodes to pool on deletion
   - Zero fragmentation for uniform workloads

4. **mmap-based allocation (for on-disk HNSW):**
   - Map a large file into memory
   - Sub-allocate from the mapped region
   - OS handles page management
   - Works well for read-heavy workloads

**Memory overhead comparison:**
```
Naive (malloc per node):     N * (node_size + 16-40 bytes) = +1.6-4 GB overhead
Slab allocator:              N * node_size + 64KB per slab = +64KB overhead
Arena allocator:             N * node_size (contiguous)    = +0 overhead
mmap allocator:              N * node_size (page-aligned)  = +~100MB overhead
```

**Qdrant's current approach:**
- Uses Rust's Vec and Box for node storage
- Segments pre-allocate based on `max_indexing_threads` and expected node count
- No explicit slab allocator (relies on Rust's allocator)
- Fragmentation is moderate for mixed-size nodes

**DB-Strike implementation plan:**
- Use arena allocator for HNSW graph construction (zero fragmentation)
- Switch to slab allocator for steady-state (supports deletions)
- For mmap mode: pre-allocate fixed-size file, mmap the entire thing
- Target: <100 MB overhead for 100M nodes (vs Qdrant's ~1-2 GB)

## 9. Cache-Oblivious Data Structures for Vector Search

### Cache-Friendly Memory Layouts

**The problem with standard HNSW:**
- Neighbor lists are scattered in memory (pointer chasing)
- Each graph traversal step requires random memory access
- Cache miss rate: ~50-80% for large datasets
- Each cache miss costs ~100ns (RAM) or ~10,000ns (SSD)

**Cache-oblivious techniques:**

1. **B-tree layout for neighbor lists (from cache-oblivious B-tree literature):**
   - Store neighbor lists in a B-tree structure
   - Automatically cache-friendly at all cache levels
   - No knowledge of cache sizes needed
   - Trade-off: O(log N) lookup vs O(1) for flat array

2. **Z-order (Morton) curve ordering:**
   - Reorder nodes by Z-order curve in the vector space
   - Nearby nodes in the curve are nearby in vector space
   - Graph traversal follows Z-order roughly, so cache hits improve
   - Requires periodic reordering (expensive for dynamic indices)

3. **Cache-line aligned neighbor lists:**
   - Align each neighbor list to a 64-byte cache line boundary
   - Store degree + neighbors in the same cache line
   - First neighbor is always in the same cache line as the degree
   - Simple to implement, ~10-20% cache hit improvement

4. **SoA (Structure of Arrays) for vector storage:**
   - Instead of AoS (vector_0 = [d0,d1,...d767]), store SoA (d0 = [v0,v1,...vN])
   - Better SIMD utilization (all coordinates of same dimension contiguous)
   - Better cache utilization for partial-dimension operations (Matryoshka)
   - Trade-off: worse for single-vector operations

5. **BFS-ordered graph traversal:**
   - During graph construction, order nodes by BFS distance from entry point
   - Store nodes in BFS order in memory
   - Search naturally follows BFS, so memory accesses are sequential
   - Can improve cache hit rate by 30-50%

6. **Prefetching:**
   - Software prefetch hints for next-node neighbor lists
   - `__builtin_prefetch(&neighbor_list[next_node])` before distance computation
   - Overlaps memory latency with computation
   - ~10-30% speedup on large datasets

**Production implementations:**
- **FAISS:** Uses cache-line aligned vectors, prefetching in hot loops
- **DiskANN:** Contiguous graph storage on SSD, sequential reads
- **hnswlib:** No explicit cache optimization (plain pointer-based)
- **Qdrant:** Basic prefetching in SIMD scoring loops

**DB-Strike implementation plan:**
- Phase 1: Cache-line align neighbor lists (64B alignment)
- Phase 2: BFS-order node storage for read-heavy workloads
- Phase 3: Software prefetching in graph traversal hot loop
- Phase 4: SoA layout for vector storage (if using partial-dimension search)

## 10. Recent Papers on Memory-Efficient ANN Search

### Key Papers (2023-2026)

**1. TurboQuant (2026) - Zandieh et al.**
- arXiv:2504.19874
- Rotation-based quantization with universal codebooks
- 4-bit: competitive with SQ at half the storage
- 1-bit: 9-21 pp better recall than BQ at same storage
- No per-dataset training needed
- Qdrant implementation in v1.18

**2. RaBitQ (2024) - Gao & Long**
- arXiv:2405.12497
- Rotation + asymmetric quantization
- Per-vector length renormalization (4 bytes overhead)
- Bit-plane scoring for 1-bit (AND + popcount)
- Used in Qdrant's TurboQuant extensions

**3. AiSAQ (2024) - Kioxia/Tatsuno et al.**
- arXiv:2404.06004
- All data on SSD, ~10 MB RAM for billion-scale
- PQ codes + graph structure entirely on storage
- Fast index switching (multiple billion-scale indices)
- DiskANN-based implementation

**4. IP-DiskANN (2025) - Microsoft**
- arXiv:2502.13826
- In-place updates of graph indices (no batch consolidation)
- Stable recall over lengthy update streams
- Better than FreshDiskANN and HNSW for streaming

**5. FreshDiskANN (2021) - Microsoft**
- arXiv:2105.09613
- Real-time insertions/deletions on disk-based graph
- 5-10x cheaper than periodic rebuilds
- >95% recall@5 with 1000+ concurrent operations/sec

**6. DiskANN (2019) - Microsoft**
- NeurIPS 2019
- Billion-point search on 64GB RAM + SSD
- Vamana graph: more versatile than HNSW for disk-based
- >5000 QPS with <3ms latency on SIFT1B

**7. FilteredDiskANN (2023)**
- Predicate pushdown for vector+attribute queries
- 2+ orders of magnitude better than post-filtering
- Graph-aware filtering (not just post-filter)

**8. DistributedANN (2025)**
- Single logical index across 1000 machines
- 6x higher efficiency than sharded indices
- 50 billion points on distributed cluster

**9. OOD-DiskANN (2022)**
- arXiv:2211.12850
- Handles out-of-distribution queries
- Efficient for queries that don't match index training distribution

**10. Matryoshka Representation Learning (2023)**
- Embedding models that support variable dimensionality
- 256-dim prefix captures most information
- Reduces memory 6x for search (1536 -> 256)
- Full-dim rerank only for top-K

### Emerging Trends (2025-2026):

1. **Quantized-only search** (no f32 rerank) becoming standard at scale
2. **SSD-native indices** (AiSAQ, DiskANN3) replacing RAM-first designs
3. **In-place graph updates** (IP-DiskANN) eliminating rebuilds
4. **Rotation-based quantization** (TurboQuant, RaBitQ) replacing learned codebooks
5. **Composable index libraries** (DiskANN3 Provider API) for database integration

**Current Qdrant approach (worst case):**
```
f32 vectors:     307 GB
HNSW graph:       13 GB
Quantized (TQ4):  38 GB  (if enabled)
Payload:          varies
Total:           358+ GB RAM
```

**DB-Strike target (aggressive):**
```
HNSW graph (mmap'd):     13 GB (page cache, ~2 GB hot)
TQ4 vectors (in RAM):    38 GB
f32 vectors (mmap'd):     0 GB in RAM (~307 GB on SSD)
Payload (mmap'd):         varies
Total RAM:               ~55 GB
```

**DB-Strike target (ultra-aggressive):**
```
HNSW graph (mmap'd):     13 GB (page cache)
TQ4 vectors (mmap'd):    38 GB (page cache)
f32 vectors (mmap'd):     0 GB in RAM
Total RAM:               ~15 GB (working set)
```

### Implementation Priority

1. **Phase 1 (Quick win):** Quantized-only HNSW (no f32 rerank) -- saves 2x memory immediately
2. **Phase 2:** mmap for HNSW graph + vectors -- enables >100M on single node
3. **Phase 3:** TurboQuant/RaBitQ implementation -- 8x compression with SQ-level recall
4. **Phase 4:** Cache-optimized graph storage (BFS ordering + prefetching)
5. **Phase 5:** Delta-encoded adjacency lists (30-50% graph memory savings)
