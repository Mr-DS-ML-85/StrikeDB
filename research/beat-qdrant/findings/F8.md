## 1. Hnsw struct fields (lines 1608–1671) — all used, but `all_f32` is unconditional

**Status:** No dead fields. Every field is referenced in insert, search, or merge paths.

**However, `all_f32` (line 1632) is always allocated even when `f32_tier` is active.** The tiered path sets `merged.all_f32 = Vec::new()` at line 3442 *after* merge, but `merge_segments` at line 2972 does `Vec::with_capacity(total * dim)` for `all_f32` before the tier check at line 3003. In tiered mode this allocates `total * dim * 4` bytes of RAM only to be dropped.

| Line | Issue | Waste |
|------|-------|-------|
| 2972 | `merged.all_f32 = Vec::with_capacity(total * dim)` — always pre-sized, even when `tier` is `Some` and all f32 writes go to mmap | `total * dim * 4` bytes wasted (e.g. 1.5 GB at 1M×384d) until drop at 3442 |
| 3442 | `merged.all_f32 = Vec::new()` drops the allocation after merge — correct, but the peak is avoidable | Peak RSS spike during merge |

**Fix:** Move the `all_f32` capacity inside the `else` branch:
```rust
if tier.is_some() {
    merged.all_f32 = Vec::new(); // no-op; writes go to mmap
} else {
    merged.all_f32 = Vec::with_capacity(total * dim);
}
```

## 2. `insert_attr` (lines 1796–1882) — unnecessary per-insert allocations

| Line | Issue | Waste |
|------|-------|-------|
| 1833 | `let mut q = Vec::with_capacity(vector.len())` — allocates a new `Vec<i8>` on every insert, even though `self.qbuf` (line 1648) is a reusable scratch buffer for exactly this purpose | 1 alloc + 1 dealloc per insert (dim bytes, e.g. 768 bytes at 768d) |
| 1836 | `std::env::var_os("DBSTRIKE_DEBUG")` — called on **every insert** to check an env var. `std::env::var_os` does a system call (getenv) each time. In a hot insert loop at 100K+ inserts, this is measurable overhead | syscall per insert |

**Fix for 1833:** Use `self.qbuf` instead of a fresh `Vec`:
```rust
self.qbuf.clear();
quantize_into(&vector, &mut self.qbuf);
let q = &self.qbuf;  // use slice reference
// ... all subsequent code uses &q (already &[i8] via Deref)
```
Note: `q` is later passed to `extend_from_slice` and `pack_current` which take `&[i8]`, so a slice reference works.

**Fix for 1836:** Cache the env check at construction time:
```rust
struct Hnsw {
    // ...
    debug: bool,
}
// In new():
debug: std::env::var_os("DBSTRIKE_DEBUG").is_some(),
```

## 3. `build_segment` and `merge_segments` (lines 2920–3107) — redundant data copies

### 3a. `build_segment` per-row `to_vec` (line 2924)

| Line | Issue | Waste |
|------|-------|-------|
| 2924 | `let v: Vec<f32> = data[(off + row) * dim..(off + row + 1) * dim].to_vec()` — allocates a fresh `Vec<f32>` per row, only to pass it to `insert_attr` which immediately copies it into `all_f32` and quantizes it | 1 alloc + N f32 copies per row |

**Fix:** Add an `insert_slice` method that takes `&[f32]` instead of `Vec<f32>`. The caller avoids the heap allocation; the callee can `extend_from_slice` directly. Alternatively, reuse a single row buffer:
```rust
let mut row_buf = vec![0.0f32; dim];
for row in 0..count {
    row_buf.copy_from_slice(&data[(off + row) * dim..(off + row + 1) * dim]);
    h.insert_attr(base_id + row as u64, row_buf.clone(), attrs[off + row]);
}
```
(Still one clone per row, but no heap alloc/dealloc cycle.)

### 3b. `merge_segments` neighbor remapping (line 2996)

| Line | Issue | Waste |
|------|-------|-------|
| 2994–2997 | For every node in every segment, a fresh `Vec<usize>` is allocated for each level's remapped neighbors, then pushed into `neigh` | O(total_nodes × levels) small Vec allocs. At 1M nodes × ~4 levels avg, ~4M small Vecs |

**Fix:** This is inherent to the Node struct design (neighbors are `Vec<Vec<usize>>`). A more compact representation (flat adjacency + offsets) would eliminate these, but that's a larger refactor. The current approach is correct; the waste is structural.

### 3c. `merge_segments` bridge pass — `to_vec()` per node (line 3077)

| Line | Issue | Waste |
|------|-------|-------|
| 3077 | `let q = merged.all_i8[ga * dim..ga * dim + dim].to_vec()` — allocates a `Vec<i8>` per node in the outer loop of the bridge pass | total × dim bytes of alloc/dealloc (e.g. 768 bytes × 1M = 768 GB of cumulative alloc traffic, though at O(1) amortized) |
| 3079 | `let mut scored: Vec<(f32, usize)> = Vec::new()` — fresh Vec per node | Small alloc per node |

**Fix for 3077:** Declare a scratch buffer outside the loop and reuse:
```rust
let mut q_buf: Vec<i8> = vec![0; dim];
for ga in 0..total {
    q_buf.copy_from_slice(&merged.all_i8[ga * dim..ga * dim + dim]);
    // use &q_buf instead of &q
}
```
**Fix for 3079:** Pre-allocate with capacity `k_seg`:
```rust
let mut scored: Vec<(f32, usize)> = Vec::with_capacity(k_seg);
// and clear() at the top of each iteration
```

### 3d. `merge_segments` entry vectors (lines 3214–3221)

## 4. `build_parallel_tiered` (lines 3346–3444) — shuffle copy, thread data sharing

| Line | Issue | Waste |
|------|-------|-------|
| 3358 | `let mut perm: Vec<usize> = (0..n).collect()` — O(n) allocation for permutation | Necessary; n × 8 bytes |
| 3366–3368 | `let shuffled: Vec<f32> = perm.iter().flat_map(...).collect()` — **full copy of the entire dataset** in shuffled order | **n × dim × 4 bytes** (e.g. 1.5 GB at 1M×384d). This is the dominant memory waste in the build path. |
| 3397 | `let zero_attr: Vec<u32> = vec![0u32; n]` — allocates n × 4 bytes of zeros | n × 4 bytes (4 MB at 1M). Could use `repeat(0).take(n)` lazily, but the Arc wrapping makes this moot. |
| 3400–3402 | Three `Arc<Vec<T>>` wrappers over `shuffled`, `perm`, `zero_attr` | Arc overhead: 3 × (n × sizeof(T) + 16 bytes header). The data is still 1.5 GB + perm + attrs. |
| 3422–3425 | `h.id_to_idx.clear()` then re-insert — clears the HashMap built by `build_segment` and rebuilds it with new ids | O(segment_size) extra work. Minor. |
| 3389 | Single-thread fallback: `let v: Vec<f32> = data[i * dim..(i + 1) * dim].to_vec()` — per-row alloc | Same as 3a above. |

**Major finding — shuffle copy is unavoidable but suboptimal:**

The full dataset is copied into `shuffled` (line 3366) so that each thread's shard is contiguous in memory. Without this, threads would read scattered rows from the original `data`, causing cache misses. **The copy is architecturally correct but doubles peak RAM during build.**

**Mitigation (partial):** Instead of copying all f32 data, shuffle the *indices* and pass an index indirection to `build_segment`. Each thread reads `data[perm[local] * dim ..]` with a random-access pattern. This trades the full copy for index-gather (n × 8 bytes vs n × dim × 4 bytes). At 768d, this saves 768× memory:
```rust
// Instead of shuffling data, let build_segment index through perm:
fn build_segment_indirected(data: &[f32], dim: usize, perm: &[usize], 
                             off: usize, count: usize, base_id: u64, attrs: &[u32]) -> Hnsw {
    let mut h = Hnsw::new();
    h.dim = dim;
    for row in 0..count {
        let src = perm[off + row];
        let v = &data[src * dim..(src + 1) * dim];
        h.insert_attr_slice(base_id + row as u64, v, attrs[src]);
    }
    h
}
```

## 5. `search_ef` (lines 4131–4155) — per-query allocations that could be pooled

| Line | Issue | Waste |
|------|-------|-------|
| 4132 | `let mut q = query.to_vec()` — allocates `dim` f32s per query | 1 alloc per query |
| 4134 | `let qq = quantize(&q)` — allocates `dim` i8s per query (calls `quantize` not `quantize_into`) | 1 alloc per query |
| 4136 | `let qf = g.query_f32(&q)` — allocates a `Vec<f32>` per query (line 2247: `q.to_vec()` or `vec![0.0; tp.d]`) | 1 alloc per query |
| 4141–4152 | `let mut rescored: Vec<(u64, f32)> = candidates.into_iter().filter_map(...).collect()` — fresh Vec for results | 1 alloc per query |

**Total: 4 heap allocations per single query.** At QPS=1000, that's 4000 allocs/sec.

**Fix:** Pool scratch buffers in `VectorIndex`:
```rust
struct VectorIndex {
    // ...
    query_scratch: Mutex<QueryScratch>,
}
struct QueryScratch {
    qn: Vec<f32>,        // dim
    qq: Vec<i8>,         // dim
    qf: Vec<f32>,        // dim or 0
    rescored: Vec<(u64, f32)>,  // pre-sized to rerank_k
}
```
`search_ef` borrows the scratch under the Mutex, clears instead of allocates, and returns only the final `Vec<(u64, f32)>` which is the output. **This eliminates 3 of 4 allocs per query.**

| Line | Issue | Waste |
|------|-------|-------|
| 4209 | `let g = self.hnsw.read().unwrap()` — correct; single lock acquire for batch. **Good.** | — |
| 4213–4216 | Pre-allocated scratch buffers `qn`, `qq`, `qf`, `rescored`. **Good — reused across queries.** | — |
| 4227 | `qf.extend_from_slice(&g.query_f32(&qn))` — `query_f32` at line 2247 allocates a **new `Vec<f32>`** internally, then `extend_from_slice` copies it into the reused `qf`. | 4247 | `rescored.clone()` — **full clone of the result Vec** inside the iterator. **Fix for 4227:** Add `query_f32_into` that writes into a pre-existing buffer (like `quantize_into` does for quantization):
```rust
fn query_f32_into(&self, q: &[f32], out: &mut Vec<f32>) {
    out.clear();
    match self.quant {
        QuantMode::Turbo1 | ... => {
            if let Some(tp) = &self.turbo {
                out.resize(tp.d, 0.0);
                for (i, &x) in q.iter().enumerate().take(tp.dim) {
                    out[i] = x * tp.aniso_scales[i];
                }
                hadamard(out);
            }
        }
        QuantMode::Product => out.extend_from_slice(q),
        _ => {},
    }
}
```

**Fix for 4247:** Instead of cloning, collect results directly:
```rust
// Instead of: rescored.clone()
// Collect into the final output Vec directly:
let mut result = Vec::with_capacity(k);
result.extend(rescored.drain(..k));
// but rescored is reused... 
// Actually: just use mem::take or swap:
let mut out = std::mem::take(&mut rescored);
out.truncate(k);

// Then on next iteration, the old buffer is reused via take.
```

## 7. The `all_f32` mirror — is it always needed? Could it be lazy?

**Current behavior:** `all_f32` (line 1632) stores the full f32 copy of every vector. It is used by:
- `vec_at_f32()` (line 1769) — called during search rerank
- `merge_segments` — copies from source segments
- `export_vectors` — reads for rebuild

**When `f32_tier` is active:** `all_f32` is emptied (line 3442) and all reads go through the mmap. So `all_f32` is redundant with `f32_tier`.

**When `f32_tier` is NOT active (default RAM path):** `all_f32` is the sole source of f32 data. It is **always needed** for the rerank stage. Making it lazy would not help because every search touches it.

**However:** In `insert_attr` at line 1882, `self.all_f32.extend_from_slice(&vector)` always stores the f32 even if the graph is only used for int8 search (no rerank). If a caller knows it will never need f32 rerank, `all_f32` could be made optional:
```rust
all_f32: Option<Vec<f32>>,  // None = no rerank, saves n × dim × 4 bytes
```
And `search_ef` would skip the f32 rerank stage, falling back to int8-only results. **This is a valid optimization for latency-insensitive workloads where 4× memory matters more than ~2% recall.**

## 8. The `all_bin` storage — any redundancy with `all_i8`?

**Lines 1612–1616:** `all_i8` stores the quantized i8 vector. `all_bin` stores the low-bit packed form (Binary/Binary2/Binary15/Turbo/Product).

**Are they redundant?** No. They serve different purposes:
- `all_i8` — used for int8 dot product (the fast traversal distance)
- `all_bin` — used for low-bit or Turbo scoring during traversal (when `quant != Int8`)

**However**, when `quant == Int8`, `all_bin` is empty (never populated). When `quant == Binary` or similar, **both** `all_i8` AND `all_bin` exist. This is because `all_i8` is always populated (line 1862: `self.all_i8.extend_from_slice(&q)`), and `all_bin` is populated additionally (line 1866: `self.all_bin.extend_from_slice(&self.bin_scratch)`).

**The question is: is `all_i8` needed when `all_bin` is the primary distance metric?**

Looking at `node_dist` (line 1520):
- `Binary` mode uses `all_bin` for distance (line 1537)
- `Turbo` mode uses `all_bin` for distance BUT falls back to `all_i8` when `qf32` is empty during construction (line 1555)
- `Int8` mode uses only `all_i8` (line 1534)

**Verdict:** `all_i8` is needed as a fallback during construction (before Turbo/PQ params are fitted). After fitting, in Binary/Turbo/Product modes, `all_i8` is **dead weight** — it is never read for distance but still consumes `n × dim` bytes. At 1M×384d, that's 384 MB of wasted RAM.

**Fix:** After `fit_quant` is called, optionally drop `all_i8` and keep only `all_bin`:
```rust
fn fit_quant(&mut self, sample: &[Vec<f32>]) {
    // ... fit params ...
    if self.quant != QuantMode::Int8 {
        // all_i8 is no longer needed for distance — drop it.
        self.all_i8 = Vec::new();
    }
}
```
Then update `node_dist` to handle the `None` case (or just not pass `all_i8` for non-Int8 modes). This saves `n × dim` bytes.

## 9. The `visited` buffer — is the `UnsafeCell` approach optimal?

**Current design (lines 1641–1646, 1712–1731):**
- `visited_cell: UnsafeCell<Vec<u32>>` — generation-stamped visited buffer
- `epoch_cell: UnsafeCell<u32>` — monotonic counter
- `bump_epoch()` increments epoch; on wraparound (every 2³² searches), zeroes the buffer
- `ensure_visited(n)` grows the buffer if needed, then bumps epoch

**Analysis:**

| Aspect | Assessment |
|--------|-----------|
| **No memset per search** | Good — epoch stamping avoids O(N) memset. Correct. |
| **No per-query alloc** | Good — buffer is reused across all searches. |
| **UnsafeCell for &self access** | Necessary because `search_layer` takes `&[Node]` (from `&self`) AND `&mut [u32]` (from the same `&self`). Without UnsafeCell, the borrow checker would reject this. |
| **`unsafe impl Sync for Hnsw`** (line 1606) | **Dangerous but correct** — Hnsw is always behind `RwLock`, so only one thread accesses the UnsafeCell fields at a time. |
| **Wraparound handling** (lines 1716–1719) | On epoch wrap, zeroes the entire buffer with `for_each`. This is O(N) but happens once per 2³² searches — negligible. |

**Potential issue:**
- **Line 2987:** `merged.visited_cell = UnsafeCell::new(vec![0u32; total])` — allocates a fresh `total`-sized buffer during merge. But `merge_segments` does not use the visited buffer (it's a structural merge, not a search). This allocation is wasted.
- **Line 3192:** `unsafe { *self.visited_cell.get() = vec![0u32; self.nodes.len()] }` — same issue in `merge_into`. Allocates a new visited buffer during a merge, even though the existing one could be resized in place.

**Fix for 2987:** Don't allocate visited_cell in merge_segments at all — it will be properly sized on first search:
```rust
merged.visited_cell = UnsafeCell::new(Vec::new()); // lazy init on first search
```

**Fix for 3192:** Resize instead of replacing:
```rust
unsafe {
    let v = &mut *self.visited_cell.get();
    if v.len() < self.nodes.len() {
        v.resize(self.nodes.len(), 0);
    } else {
        v.fill(0); // only zero if shrink happened (rare)
    }
}
```

**Overall:** The UnsafeCell approach is optimal for the single-writer-within-RwLock model. No better alternative exists without switching to `RefCell` (which has runtime borrow checks and can't work through `&self`).
