### Level Generation Formula

```rust
// From graph_layers_builder.rs
level_factor: 1.0 / (max(hnsw_m.m, 2) as f64).ln()

pub fn get_random_layer<R>(&self, rng: &mut R) -> usize {
    let distribution = Uniform::new(0.0, 1.0).unwrap();
    let sample: f64 = rng.sample(distribution);
    let picked_level = -sample.ln() * self.level_factor;
    picked_level.round() as usize
}
```

**Formula**: `level = round(-ln(U(0,1)) / ln(max(M,2)))`  
This is the standard HNSW geometric distribution, matching Malkov & Yashunin.

## 2. Graph Construction: Parallel vs Single-Threaded

### Single-Threaded Warm-Up Phase

```rust
// From hnsw.rs (build.rs)
pub const SINGLE_THREADED_HNSW_BUILD_THRESHOLD: usize = 256;  // release
pub const SINGLE_THREADED_HNSW_BUILD_THRESHOLD: usize = 32;   // debug
```

**Strategy**:
1. First 256 points (release) are inserted **single-threaded** to ensure the graph has a solid core structure
2. This prevents disconnected components in the early graph
3. After the warm-up phase, remaining points are inserted in parallel via rayon

```rust
// From build.rs
let mut ids = Vec::with_capacity(total_vector_count);
let mut first_few_ids = Vec::with_capacity(SINGLE_THREADED_HNSW_BUILD_THRESHOLD);

// ... separate first 256 from rest

// Single-threaded phase
for vector_id in first_few_ids {
    insert_point(vector_id)?;
}

// Parallel phase using rayon
if !ids.is_empty() {
    pool.install(|| ids.into_par_iter().try_for_each(insert_point))?;
}
```

### Parallel Construction via Rayon

```rust
let pool = rayon::ThreadPoolBuilder::new()
    .thread_name(|idx| format!("hnsw-build-{idx}"))
    .num_threads(permit.num_cpus as usize)
    .spawn_handler(|thread| {
        // On Linux, use lower thread priority
        #[cfg(target_os = "linux")]
        if let Err(err) = linux_low_thread_priority() {
            log::debug!("Failed to set low thread priority...");
        }
        thread.run()
    })
    .build()?;
```

**Key details**:
- Uses rayon thread pool with configurable thread count
- On Linux, threads are set to low priority to minimize impact on serving traffic
- Each parallel insert acquires `RwLock` on the target node's links

### Thread Priority

```rust
#[cfg(target_os = "linux")]
use common::cpu::linux_low_thread_priority;

// Threads are spawned with low priority

    log::debug!("Failed to set low thread priority for HNSW building, ignoring: {err}");
}
```

## 3. Graph Pruning Strategy (Heuristic)

### Yes, They Use the Heuristic from Malkov & Yashunin Alg. 4

```rust
// From hnsw.rs
const HNSW_USE_HEURISTIC: bool = true;
```

### Implementation in links_container.rs

```rust
pub fn fill_from_sorted_with_heuristic(
    &mut self,
    candidates: impl Iterator<Item = ScoredPointOffset>,
    level_m: usize,
    mut score: impl FnMut(PointOffsetType, PointOffsetType) -> ScoreType,
) {
    self.links.clear();
    if level_m == 0 {
        self.processed_by_heuristic = 0;
        return;
    }
    'outer: for candidate in candidates {
        for &existing in &self.links {
            if score(candidate.idx, existing) > candidate.score {
                continue 'outer;  // Skip if existing is closer to target
            }
        }
        self.links.push(candidate.idx);
        if self.links.len() >= level_m {
            break;
        }
    }
    self.processed_by_heuristic = self.links.len() as u32;
}
```

**Algorithm**: For each candidate in descending score order, add it to the list only if none of the already-selected points are closer to the candidate than the candidate itself. This is the standard HNSW heuristic.

### Heuristic Usage During Insert

```rust
fn link_new_point_on_level(...) -> ScoredPointOffset {
    let nearest = self.search_on_level(..., self.ef_construct, ...).unwrap();
    
    if self.use_heuristic {
        self.link_with_heuristic(point_id, curr_level, points_scorer, nearest);
    } else {
        self.link_without_heuristic(point_id, curr_level, points_scorer, nearest);
    }
    // ...
}

fn link_with_heuristic(...) {
    // Forward links
    let selected_nearest = existing_links.fill_from_sorted_with_heuristic(iter, level_m, scorer);
    
    // Backward links (also with heuristic)
    for &other_point in &selected_nearest {
        self.links_layers[other_point as usize][curr_level]
            .write()
            .connect_with_heuristic(point_id, other_point, level_m, scorer, &mut items);
    }
}
```

## 4. Concurrent Reads During Graph Construction

### RwLock per Node per Level

```rust
pub type LockedLinkContainer = RwLock<LinksContainer>;
pub type LockedLayersContainer = Vec<LockedLinkContainer>;
```

Each node at each level has its own `RwLock`. During construction:
- **Reads** (traversal for search) use `read()` locks
- **Writes** (inserting new links) use `write()` locks

### Ready List for Construction Safety

```rust
// From graph_layers_builder.rs
ready_list: BitVec<AtomicUsize>,

// During link traversal:
fn for_each_link<F>(&self, point_id: PointOffsetType, level: usize, mut f: F) {
    let links = self.links_layers[point_id as usize][level].read();
    for link in links.iter() {
        if self.ready_list[link as usize] {
            f(link);  // Only traverse to ready points
        }
    }
}
```

The `ready_list` is a `BitVec` that tracks which points are fully inserted. This ensures that during parallel construction, a thread only traverses to points that are completely linked.

### Entry Point Protection

```rust
entry_points: Mutex<EntryPoints>,
```

Entry points are protected by a `Mutex` to ensure thread-safe updates during construction.

## 5. Visited Buffer Implementation

### Generation-Stamped Array (NOT HashSet, NOT Bitset)

```rust
// From visited_pool.rs
struct VisitedList {
    current_iter: u8,
    visit_counters: Vec<u8>,
}
```

**Implementation**:
- Uses a `Vec<u8>` array where each element stores the "iteration number" of the last visit
- `current_iter` is a `u8` counter (wraps around at 255)
- Check is O(1): `visit_counters[point_id] == current_iter`
- Update is O(1): `visit_counters[point_id] = current_iter`

```rust
pub fn check_and_update_visited(&mut self, point_id: PointOffsetType) -> bool {
    let idx = point_id as usize;
    if idx >= self.visited_list.visit_counters.len() {
        self.visited_list.visit_counters.resize(idx + 1, 0);
    }
    std::mem::replace(
        &mut self.visited_list.visit_counters[idx],
        self.visited_list.current_iter,
    ) == self.visited_list.current_iter
}

pub fn next_iteration(&mut self) {
    self.visited_list.current_iter = self.visited_list.current_iter.wrapping_add(1);
    if self.visited_list.current_iter == 0 {
        self.visited_list.current_iter = 1;
        self.visited_list.visit_counters.fill(0);
    }
}
```

### VisitedPool (Reusable Buffer Pool)

```rust
pub struct VisitedPool {
    pool: RwLock<Vec<VisitedList>>,
}

impl VisitedPool {
    pub fn get(&self, num_points: usize) -> VisitedListHandle<'_> {
        match self.pool.write().pop() {
            None => VisitedListHandle::new(self, VisitedList::new(num_points)),
            Some(data) => {
                let mut visited_list = VisitedListHandle::new(self, data);
                visited_list.resize(num_points);
                visited_list.next_iteration();
                visited_list
            }
        }
    }
}
```

**Key insight**: The pool reuses `VisitedList` instances across queries. When a `VisitedList` is returned, it's kept in the pool (up to `POOL_KEEP_LIMIT`) to avoid allocation. On next use, `next_iteration()` is called, which simply increments the counter.

**Limitation**: `u8` counter means after 255 queries, the counter wraps and forces a `fill(0)` reset. This is a performance consideration for very high query rates.

**Source**: [visited_pool.rs](https://github.com/qdrant/qdrant/blob/master/lib/segment/src/index/visited_pool.rs)

## 6. Memory Layout: Adjacency Lists

### During Construction (Runtime)

```rust
// LinksContainer holds Vec<PointOffsetType>
pub struct LinksContainer {
    links: Vec<PointOffsetType>,
    processed_by_heuristic: u32,
}

// Each point has a Vec of RwLock<LinksContainer>, one per level
links_layers: Vec<Vec<RwLock<LinksContainer>>>,
```

**Layout**: `Vec<Vec<RwLock<LinksContainer>>>` - a vector of vectors. Each point has a variable number of levels, and each level has its own `RwLock<Vec<u32>>`.

### On Disk / After Build (GraphLinks)

Three formats supported:

1. **Plain** (`links.bin`): Simple adjacency lists
2. **Compressed** (`links_compressed.bin`): Bit-packed links with offset compression
3. **CompressedWithVectors** (`links_comp_vec.bin`): Compressed links + inline quantized vectors

```rust
pub enum GraphLinksFormat {
    Plain,
    Compressed,
    CompressedWithVectors,
}
```

### Compressed Format Layout

```
Level 0: not sorted (point IDs in insertion order)
Level > 0: sorted by number of levels (highest level first)

offsets:       [6       11     15     17]
               |       |      |      |
               v       v      v      v
indexes:  012345   6789A   BCDE   FG     H

flatten:  123456   ADBCE   adbc   ZY     7
reindex:  142350   142350  142350 142350 142350
```

**Key optimization**: Points are reordered so that higher-level points come first. This improves cache locality during multi-level search.

### Compressed with Vectors Layout

```
[base_vector] [varint_link_count] [compressed_links] [padding] [link_vectors...]
```

This allows searching entirely within the graph file without accessing vector storage (quantized vectors are inlined).

**Source**: [graph_links.rs](https://github.com/qdrant/qdrant/blob/master/lib/segment/src/index/hnsw_index/graph_links.rs)

## 7. Custom Optimizations Over Standard hnswlib

### 7.1 ACORN-1 Search Algorithm

Qdrant implements the ACORN-1 algorithm as an alternative to standard HNSW search:

```rust
pub enum SearchAlgorithm {
    Hnsw,
    Acorn,
}
```

ACORN explores 2-hop neighbors of deleted/filtered-out nodes to improve recall under filtering:

```rust
fn search_on_level_acorn(...) {
    // 1-hop: direct neighbors (scored)
    // 2-hop: neighbors of filtered-out nodes (to find border points)
    // Uses DFS instead of BFS for the deleted sub-graph
}
```

**Benefit**: Better recall for selective filters where many nodes are filtered out.

### 7.2 Inline Vector Search (GraphLinksWithVectors)

```rust
pub trait GraphLayersWithVectors: GraphLayersBase {
    fn has_inline_vectors(&self) -> bool;
    fn links_with_vectors(&self, point_id: PointOffsetType, level: usize) 
        -> (&[u8], impl Iterator<Item = (PointOffsetType, &[u8])> + '_);
}
```

When using `CompressedWithVectors` format, quantized vectors are stored directly in the graph links file. This enables:
- Single-file search (no separate vector lookup)
- Better cache locality for quantized search

### 7.3 Heuristic Caching Optimization

The `connect_with_heuristic` method in `links_container.rs` caches scores and uses order information to avoid recomputing scores for points known to be sorted:

```rust
struct Item {
```

## 8. Known Limitations & Bugs

### 8.1 Visited List u8 Counter Overflow

```rust
// visited_pool.rs
pub fn next_iteration(&mut self) {
    self.visited_list.current_iter = self.visited_list.current_iter.wrapping_add(1);
    if self.visited_list.current_iter == 0 {
        self.visited_list.current_iter = 1;
        self.visited_list.visit_counters.fill(0);  // Expensive!
    }
}
```

**Impact**: After 255 consecutive queries without resetting, the counter wraps and forces a full array clear. This could cause latency spikes under sustained high query rates.

### 8.2 No Incremental Updates

HNSW indexes are rebuilt from scratch during segment optimization. There is no incremental insert/delete support for the graph structure itself. Deleted points are simply marked and filtered during search.

### 8.3 Segment Merging Requires Graph Rebuild

When segments are merged, the HNSW graph must be rebuilt because:
- Point IDs are renumbered
- The `GraphLayersHealer` only fixes connectivity, not optimality
- The healed graph may have suboptimal link quality

### 8.4 Single-Threaded Phase Bottleneck

The first 256 points are always inserted single-threaded, which could be a bottleneck for very small segments or during rapid segment creation.

### 8.5 Linux-Only Thread Priority

Low thread priority for indexing is only implemented on Linux:

```rust
#[cfg(target_os = "linux")]
if let Err(err) = linux_low_thread_priority() {
    log::debug!("Failed to set low thread priority...");
}
```

On other platforms, indexing threads run at normal priority and may compete with search threads.

### 8.6 Compressed Format Conversion Not Production-Ready

```rust
const LINK_COMPRESSION_CONVERT_EXISTING: bool = false;
```

The plain-to-compressed conversion for existing indexes is disabled in production.

## Competitive Opportunities (for DB-Strike)

1. **Visited list**: Replace u8 generation counter with u64 or bitset for high query rates
2. **Incremental updates**: Implement true incremental HNSW instead of full rebuilds
3. **Parallel warm-up**: Consider parallel construction from the start with proper synchronization
4. **Graph healing**: Improve healed graph quality with re-optimization passes
5. **Memory layout**: Explore SoA (struct-of-arrays) for better SIMD traversal
6. **Prefetch**: Add explicit prefetch hints during graph traversal
7. **ACORN integration**: The ACORN search is only on level 0; extend to all levels
8. **Lock-free construction**: Replace per-node RwLock with lock-free data structures
