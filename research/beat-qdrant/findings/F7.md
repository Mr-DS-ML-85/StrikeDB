## 1. What is Multi-Vector Search in Qdrant? (Multiple Vectors Per Point)

Qdrant supports **two distinct concepts** for multiple vectors, which are often confused:

### A. Multivectors (v1.10.0+)
A single vector field that stores a **matrix** of same-shaped dense vectors per point. The dimension is fixed, but the number of vectors in the matrix can vary per point.

```json
// A multivector - variable number of same-dimension vectors per point
"vector": [
    [-0.013,  0.020, -0.007, -0.111],
    [-0.030, -0.055,  0.001,  0.072],
    [-0.041,  0.014, -0.032, -0.062]
]
```

**Use cases:**
1. **Multiple representations of the same object** - e.g., multiple embeddings for pictures of the same object from different angles
2. **Late interaction embeddings (ColBERT)** - token-level vectors where each token gets its own vector

**Scoring function:** Currently only `max_sim` is supported:
```
score = Σ_{i=1}^{N} max_{j=1}^{M} Sim(vectorA_i, vectorB_j)
```
Where N and M are the number of vectors in each matrix, and Sim is the base distance function (cosine, dot, etc.).

**Collection config:**
```json
{
  "vectors": {
    "size": 128,
    "distance": "Cosine",
    "multivector_config": {
      "comparator": "max_sim"
    }
  }
}
```

### B. Named Vectors (Multiple Different Vector Fields Per Point)
Named vectors allow storing **multiple vectors of different sizes and types** in the same data point. This is the primary mechanism for multimodal search.

```json
// Each point can have multiple named vector fields of different dimensions
{
  "id": 1,
  "vector": {
    "image": [0.9, 0.1, 0.1, 0.2],           // 4-dim image embedding
    "text": [0.4, 0.7, 0.1, 0.8, 0.1],       // 5-dim text embedding  
    "text-sparse": {                           // sparse vector
      "indices": [1, 3, 5, 7],
      "values": [0.1, 0.2, 0.3, 0.4]
    }
  }
}
```

**Key differences:**
- Multivectors: Same dimension, variable count, single `max_sim` comparison
- Named vectors: Different dimensions, different types (dense/sparse/multivector), independently searchable

## 2. How Qdrant Handles Image+Text Embedding Fusion

Qdrant does NOT have a built-in multimodal embedding model (like CLIP). Instead, it provides the **infrastructure** for multimodal search through:

### Architecture Pattern: Named Vectors + Prefetch Fusion
```
Document -> [Image Encoder] -> "image" vector (e.g., 768-dim)
          -> [Text Encoder]  -> "text" vector (e.g., 384-dim)
          -> Store both as named vectors on the same point
          
Query (text or image) -> Search against appropriate named vector
                       -> Fuse results via Query API
```

### Multi-Representation Search Tutorial (Official)
The official tutorial demonstrates a production pattern with arXiv papers using 4 named vectors per point:
- `dense_chunk` (384-dim) - chunk content embedding
- `dense_title` (384-dim) - title embedding
- `dense_abstract` (384-dim) - abstract embedding  
- `sparse_title` - BM25 sparse vector for title

**Collection schema:**
```python
client.create_collection(
    collection_name="arxiv_multi_repr",
    vectors_config={
        "dense_chunk":    models.VectorParams(size=384, distance=models.Distance.COSINE),
        "dense_title":    models.VectorParams(size=384, distance=models.Distance.COSINE),
        "dense_abstract": models.VectorParams(size=384, distance=models.Distance.COSINE),
    },
    sparse_vectors_config={
        "sparse_title": models.SparseVectorParams(modifier=models.Modifier.IDF),
    },
)
```

**Retrieval with RRF fusion:**
```python
results = client.query_points_groups(
    collection_name="arxiv_multi_repr",
    prefetch=[
        models.Prefetch(query=dense_query,  using="dense_chunk",    limit=100),
        models.Prefetch(query=dense_query,  using="dense_title",    limit=100),
        models.Prefetch(query=dense_query,  using="dense_abstract", limit=100),
        models.Prefetch(query=sparse_query, using="sparse_title",   limit=100),
    ],
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    group_by="document_id",
    group_size=group_size,
    limit=limit,
)
```

### Discovery API for Multimodal Vector-Space Constraints
Qdrant's Discovery API (v1.7+) enables constraining search in vector space using positive/negative pairs - useful for multimodal scenarios:
```python
# Search for items similar to a target, but constrained by multimodal context
results = client.query_points(
    collection_name="{collection_name}",
    query=models.DiscoverQuery(
        discover=models.DiscoverInput(
            target=[0.2, 0.1, 0.9, 0.7],
            context=[
                models.ContextPair(positive=100, negative=718),
                models.ContextPair(positive=200, negative=300),
            ],
        )
    ),
)
```

## 3. Named Vectors Feature (Multiple Vector Fields Per Document)

### Configuration
Each named vector can have independent:
- **Dimension/size** - different vectors can have different lengths
- **Distance metric** - Cosine for one, Dot for another, etc.
- **Type** - dense, sparse, or multivector
- **HNSW config** - independently configured indexing
- **Quantization** - per-vector quantization settings

```python
client.create_collection(
    collection_name="{collection_name}",
    vectors_config={
        "image": models.VectorParams(size=768, distance=models.Distance.DOT),
        "text": models.VectorParams(size=384, distance=models.Distance.COSINE),
        "colbert": models.VectorParams(
            size=128,
            distance=models.Distance.COSINE,
            multivector_config=models.MultiVectorConfig(
                comparator=models.MultiVectorComparator.MAX_SIM
            ),
            hnsw_config=models.HnswConfigDiff(m=0)  # disable HNSW for reranking
        ),
    },
    sparse_vectors_config={
        "text-sparse": models.SparseVectorParams(),
    },
)
```

### Dynamic Named Vectors (v1.18.0+)
Named vectors can be **added to or removed from** an existing collection without recreating:
```python
client.create_vector_name(
    collection_name="{collection_name}",
    vector_name="{vector_name}",
    vector_name_config=models.DenseVectorNameConfig(
        dense=models.DenseVectorConfig(size=256, distance=models.Distance.COSINE),
    ),
)
```

### Search with Named Vectors
Use the `using` parameter to specify which named vector to search against:
```python
results = client.query_points(
    collection_name="{collection_name}",
    query=[0.2, 0.1, 0.9, 0.7],
    using="image",  # search against the "image" named vector
    limit=3,
)
```

## 4. Query API for Multi-Vector Search

Qdrant's **Query API** (v1.10.0+) is the universal interface for multi-vector search. It uses a `prefetch` parameter for composing sub-requests.

### Core Pattern: Prefetch + Fuse
```python
results = client.query_points(
    collection_name="{collection_name}",
    prefetch=[
        models.Prefetch(query=dense_query, using="dense", limit=100),
        models.Prefetch(query=sparse_query, using="sparse", limit=100),
    ],
    query=models.RrfQuery(rrf=models.Rrf()),
    limit=10,
)
```

### Supported Query Types in Query API
1. **Nearest vector** - standard vector search
2. **Recommend** - search based on positive/negative examples
3. **Discover** - target + context pairs for constrained search
4. **Context** - search using only context pairs (no target)
5. **Fusion** - RRF or DBSF fusion of multiple prefetches
6. **Formula** - custom scoring expressions

### Nested Prefetches (Multi-Stage)
Prefetches can have their own prefetches for multi-stage pipelines:
```python
results = client.query_points(
    collection_name="{collection_name}",
    prefetch=models.Prefetch(
        prefetch=models.Prefetch(
            query=[1, 23, 45, 67],  # stage 1: small byte vector
            using="mrl_byte",
            limit=1000,
        ),
        query=[0.01, 0.299, 0.45, 0.67],  # stage 2: full dense vector
        using="full",
        limit=100,
    ),
    query=[  # stage 3: multivector reranking
        [0.1, 0.2, 0.32],
        [0.2, 0.1, 0.52],
        [0.8, 0.9, 0.93],
    ],
    using="colbert",
    limit=10,
)
```

### Grouping for Multi-Representation
Results from multiple named vectors can be grouped back to the document level:
```python
results = client.query_points_groups(
    collection_name="...",
    prefetch=[...],
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    group_by="document_id",
    group_size=3,
    limit=10,
)
```

## 5. Scoring Across Multiple Vector Fields

### Fusion Methods Available

#### Reciprocal Rank Fusion (RRF)
Combines results based on rank position, not raw scores. Handles different scoring scales automatically.
```
score(d) = Σ_{r_d ∈ R(d)} 1/(k + r_d)
```
- Default k=2 (configurable since v1.16.0)
- Supports weights since v1.17.0: `weights=[3.0, 1.0]`

#### Distribution-Based Score Fusion (DBSF) (v1.11.0+)
Normalizes scores from each retriever using 3-sigma normalization before summing:
```
ŝ = (s - (μ - 3σ)) / (6σ)
```
- Preserves score magnitude (unlike RRF)
- Works well when retrievers have well-calibrated scores

#### Custom Formula (FormulaQuery)
Full control over score combination:
```python
query=models.FormulaQuery(
    formula=models.SumExpression(sum=[
        models.MultExpression(mult=[1.0, "$score[0]"]),
        models.MultExpression(mult=[0.5, "$score[1]"]),
        models.MultExpression(mult=[0.4, "$score[2]"]),
        models.MultExpression(mult=[0.3, "$score[3]"]),
    ]),
    defaults={"$score[1]": 0.0, "$score[2]": 0.0, "$score[3]": 0.0},
)
```

### Scoring for Multivectors (MaxSim)
For multivectors, the score is computed as:
```
score = Σ_{i=1}^{N} max_{j=1}^{M} Sim(vectorA_i, vectorB_j)
```
Returns a **single combined score per point**, not per sub-vector.

### Recommendation Strategies (Multiple Vectors)
- **average_vector** (default) - averages positive/negative examples
- **best_score** - measures each candidate against every example (linearly impacted by example count)
- **sum_scores** - sums scores from all positive examples, subtracts negative scores

## 6. Performance of Multi-Vector Search vs Single-Vector

### Memory Overhead
From the official capacity planning docs:
```
memory_size = number_of_vectors * vector_dimension * 4 bytes * 1.5
```
The 1.5x multiplier accounts for metadata, indexes, and temporary segments.

**Multi-vector storage overhead:**
- Each named vector has its own HNSW index and storage
- Storing title/abstract embeddings on every chunk trades storage for query simplicity
- The multi-representation tutorial notes: 20,000 documents at 24 chunks each with duplicated vectors adds ~1.4 GB vs ~60 MB with a sidecar collection

### Indexing Optimization for Multivectors
Qdrant recommends **disabling HNSW** for vectors used only for reranking:
```python
models.VectorParams(
    size=128,
    distance=models.Distance.COSINE,
    multivector_config=models.MultiVectorConfig(
        comparator=models.MultiVectorComparator.MAX_SIM
    ),
    hnsw_config=models.HnswConfigDiff(m=0)  # Disable HNSW
)
```

**Benefits of disabling HNSW on reranking vectors:**
- Saves compute
- Reduces memory usage
- Speeds up vector uploads

### Two-Stage Search Pattern (Performance Optimization)
```
Stage 1: Fast retrieval with smaller/cheaper vector (high recall, low precision)
Stage 2: Reranking with larger/more expensive vector (high precision)
```

Examples:
1. Quantized vectors -> full-precision reranking
2. Matryoshka byte vectors -> full-length reranking
3. Dense vectors -> ColBERT multivector reranking

### Search Latency Considerations
- Each prefetch runs independently (can be parallelized)
- Fusion (RRF/DBSF) runs after all prefetches complete
- More named vectors = more prefetches = potentially higher latency
- Recommendation: tune per-prefetch `limit` based on expected overlap

Qdrant does not publish dedicated multimodal search benchmarks. However:

### Related Benchmark Data

## 8. Recommended Collections/Configs for Multimodal

### Official Recommended Pattern (Multi-Representation Tutorial)

```python
# Single collection with named vectors per modality
client.create_collection(
    collection_name="multimodal_docs",
    vectors_config={
        "dense_chunk":    models.VectorParams(size=384, distance=models.Distance.COSINE),
        "dense_title":    models.VectorParams(size=384, distance=models.Distance.COSINE),
        "dense_abstract": models.VectorParams(size=384, distance=models.Distance.COSINE),
    },
    sparse_vectors_config={
        "sparse_title": models.SparseVectorParams(modifier=models.Modifier.IDF),
    },
)

# Index metadata for filtering and grouping
client.create_payload_index(
    collection_name="multimodal_docs",
    field_name="document_id",
    field_schema=models.PayloadSchemaType.KEYWORD,
)
```

### ColBERT + Dense Reranking Pattern
```python
client.create_collection(
    collection_name="dense_multivector_demo",
    vectors_config={
        "dense": models.VectorParams(
            size=384,
            distance=models.Distance.COSINE
            # HNSW ON for retrieval
        ),
        "colbert": models.VectorParams(
            size=128,
            distance=models.Distance.COSINE,
            multivector_config=models.MultiVectorConfig(
                comparator=models.MultiVectorComparator.MAX_SIM
            ),
            hnsw_config=models.HnswConfigDiff(m=0)  # HNSW OFF for reranking
        )
    }
)
```

### Design Principles
1. **One collection, multiple named vectors** - simpler than separate collections
2. **Title/abstract vectors duplicated across chunks** - trades storage for query simplicity
3. **Disable HNSW on reranking-only vectors** - save memory and compute
4. **Index document_id for grouping** - essential for multi-representation results
5. **Use RRF as default fusion** - handles different scoring scales automatically
6. **Tune per-prefetch limits** - balance recall vs latency

## 9. Handling Different Vector Dimensions in the Same Collection

### Named Vectors = Different Dimensions Supported
Qdrant explicitly supports different vector dimensions per named vector:

```python
client.create_collection(
    collection_name="{collection_name}",
    vectors_config={
        "image": models.VectorParams(size=768, distance=models.Distance.DOT),   # 768-dim
        "text": models.VectorParams(size=384, distance=models.Distance.COSINE), # 384-dim
        "title": models.VectorParams(size=128, distance=models.Distance.COSINE), # 128-dim
    },
)
```

### Each Named Vector Has Independent:
- **Dimension (size)** - can be any positive integer
- **Distance metric** - Cosine, Dot, Euclid, Manhattan
- **HNSW config** - m, ef_construct, full_scan_threshold
- **Quantization** - scalar, product, or binary quantization
- **On-disk storage** - per-vector on_disk setting
- **Multivector config** - optional multivector comparator

### Dynamic Dimension Changes (v1.18.0+)
Named vectors can be added or removed from existing collections:
```python
# Add a new named vector with different dimensions
client.create_vector_name(
    collection_name="{collection_name}",
    vector_name="new_modality",
    vector_name_config=models.DenseVectorNameConfig(
        dense=models.DenseVectorConfig(
            size=512,  # different dimension
            distance=models.Distance.COSINE,
        ),
    ),
)
```

### Limitations
- Within a single named vector field, all points must have the **same dimension**
- Different named vectors CAN have different dimensions
- Multivectors within a named vector field must all have the **same sub-vector dimension**, but can have **variable number of sub-vectors**

## Summary: Key Takeaways for Beating Qdrant

### Qdrant Strengths
1. **Flexible named vectors** - multiple modalities, dimensions, types in one collection
2. **Powerful Query API** - prefetch + fusion + grouping in one request
3. **Multiple fusion methods** - RRF, DBSF, custom formulas
4. **Native multivector support** - ColBERT/late interaction without workarounds
5. **Dynamic schema** - add/remove named vectors without recreation

### Qdrant Weaknesses / Opportunities to Beat
1. **No built-in multimodal embedding** - requires external model orchestration
2. **No published multimodal benchmarks** - opportunity to demonstrate superior performance
3. **Memory overhead of named vectors** - duplicated vectors across chunks can be expensive
4. **MaxSim is the only multivector comparator** - limited flexibility for custom fusion
5. **No native cross-attention fusion** - relies on rank fusion, not learned fusion
6. **Storage tradeoff** - official tutorial acknowledges 23x storage overhead for query simplicity (1.4 GB vs 60 MB)
7. **Fusion is post-hoc** - cannot do true joint embedding space search across modalities
8. **No learned reranker integration** - FormulaQuery is hand-tuned, not learned

### Potential Differentiators
1. **Native multimodal embedding** - built-in CLIP/ALIGN support
2. **Learned fusion** - neural fusion instead of RRF/DBSF
3. **Better storage efficiency** - avoid vector duplication across representations
4. **Published multimodal benchmarks** - demonstrate quality and performance advantages
5. **Cross-modal native scoring** - score across modalities in a unified space
6. **Streaming multimodal index** - real-time multimodal updates without reindexing
