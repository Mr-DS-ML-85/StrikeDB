# F4: Vector Quantization Techniques for ANN Search — Landscape & Tradeoffs

> Compiled 2026-07-18. All claims include source and confidence rating.

---

## 1. INT8 Scalar Quantization

**Claim** | Scalar quantization maps float32 vectors to int8 via `q[i] = round(x[i] * 127)` after L2-normalization (values in [-1,1]). Memory drops 4x; SIMD compute density goes from 8 f32 lanes to 32 i8 lanes per AVX2 register. | Source: DB-Strike `vector.rs` lines 1-18, Google ScaNN paper [arXiv:1908.10396] | Confidence: **high**

**Claim** | Recall loss from INT8 scalar quantization is typically 1-2% at 384-1536 dimensions. The error is negligible for high-dimensional vectors. | Source: Qdrant quantization docs; Qdrant benchmark data across 10 datasets | Confidence: **high**

**Claim** | Scalar quantization achieves 4x compression with search speedup from SIMD int8 dot products — `_mm256_cvtepi8_epi16` + `_mm256_madd_epi16` processes 16 i8 pairs per instruction. | Source: DB-Strike `vector.rs` lines 15-17 | Confidence: **high**

**Claim** | The cosine distance derivation for unit vectors: `dot(q_i8, x_i8) ≈ dot(q_f32, x_f32) * 127²`, so `cos_dist = 1 - (dot_i8 / 16129)`. | Source: DB-Strike `vector.rs` line 29 | Confidence: **high**

**Claim** | Qdrant's SQ uses a `quantile` parameter (default 0.99) to handle outliers — clipping the top 1% of extreme values from quantization bounds improves recall without affecting memory. | Source: Qdrant quantization documentation | Confidence: **high**

**Claim** | TurboQuant 4-bit at 8x compression is competitive with SQ at 4x — within ~1-2 percentage points on most datasets, and sometimes *ahead* of SQ where the int8 grid struggles with the embedding distribution. On 3 of 10 Qdrant datasets (dbp-oai, cohere, laion), TQ 4-bit beats SQ by up to 4.6 pp. | Source: Qdrant TurboQuant blog (May 2026), benchmark table with 10 datasets | Confidence: **high**

## 2. Product Quantization (PQ)

**Claim** | PQ splits a D-dimensional vector into m subvectors, runs k-means on each subspace independently, and replaces each subvector with a single centroid ID. For D=128, m=8, nbits=8 (256 centroids): original 128x32=4096 bytes becomes 8x8=64 bytes — a 64x compression. | Source: Pinecone PQ tutorial (2024) | Confidence: **high**

**Claim** | PQ requires training on representative data — the k-means codebooks must be learned from a dataset several times larger than k. Without product subquantization, training needs kD parameters; with PQ, training needs only k*^(1/m) per subspace, but still requires substantial calibration data. | Source: Pinecone PQ tutorial; Jégou et al., "Product quantization for nearest neighbor search" (2010) | Confidence: **high**

**Claim** | In Faiss benchmarks on Sift1M (1M x 128d), IndexPQ achieves ~50% recall vs flat (100%), with 1.49ms vs 15ms search time and 6.5MB vs 256MB memory (98.4% reduction). IndexIVFPQ with nprobe=48 achieves 52% recall at 0.09ms (170x faster than flat). | Source: Pinecone PQ tutorial Faiss benchmarks | Confidence: **medium** (specific to Sift1M; other datasets vary)

**Claim** | PQ distance calculations are not SIMD-friendly, making it slower than scalar quantization in practice despite higher compression. The asymmetric/asymmetric distance estimation between codebook entries is expensive. | Source: Qdrant quantization docs; Pinecone PQ tutorial | Confidence: **high**

**Claim** | TurboQuant consistently achieves superior recall ratios compared to PQ baselines (including RabbiQ) on vector search benchmarks, despite those baselines utilizing larger codebooks and dataset-specific tuning. TurboQuant indexing time is "virtually zero" vs PQ's training requirement. | Source: TurboQuant paper [arXiv:2504.19874] (ICLR 2026) | Confidence: **high**

**Claim** | PQ is recommended only when memory footprint is the absolute top priority and accuracy/speed are not critical — it supports up to 64x compression. | Source: Qdrant quantization documentation | Confidence: **high**

## 3. Binary Quantization (1-bit)

**Claim** | Binary quantization reduces each vector component to 1 bit (sign), achieving 32x compression. It is the fastest quantization method since vector comparison uses a few CPU instructions (Hamming distance via popcount). Can achieve up to 40x speedup vs original vectors. | Source: Qdrant quantization docs | Confidence: **high**

**Claim** | BQ works well for high-dimensional, centered vector distributions (mean near zero). Models like OpenAI `text-embedding-ada-002` (1536d) achieve 0.98 recall@100 with 4x oversampling; Cohere `embed-english-v2.0` (4096d) achieves 0.98 recall@50 with 2x oversampling. | Source: Qdrant quantization docs | Confidence: **high**

**Claim** | BQ fails on low-dimensional vectors or distributions not centered near zero. One-bit compression causes significant data loss and precision drops for vectors smaller than ~1000 dimensions, often requiring expensive rescoring. | Source: Qdrant Binary Quantization article (1.5-bit and 2-bit section) | Confidence: **high**

**Claim** | 2-bit BQ addresses the poor handling of values close to zero by explicitly representing zeros: `-1` = 00, `0` = 01, `1` = 11. 1.5-bit BQ merges buckets of element pairs into binary triplets. Both significantly outperform vanilla 1-bit BQ. | Source: Qdrant quantization docs | Confidence: **high**

**Claim** | At 16x compression, TurboQuant 2-bit beats BQ 2-bit by 9-24 pp across all 10 Qdrant benchmark datasets. At 32x, TurboQuant 1-bit beats vanilla BQ 1-bit by 9-21 pp. | Source: Qdrant TurboQuant blog (May 2026), detailed benchmark table | Confidence: **high**

**Claim** | Asymmetric BQ (1-bit storage, 8-bit query) is stronger than vanilla BQ but still trails TurboQuant 1-bit on every dataset tested, though the margin narrows (0.1-10 pp). | Source: Qdrant TurboQuant blog (May 2026) | Confidence: **high**

**Claim** | BQ is equivalent to Hamming distance: if original vectors contain {-1, 1}, then the dot product equals Hamming distance after replacing -1 with 0 and 1 with 1. This makes it efficient to compute via SIMD popcount. | Source: Qdrant quantization docs | Confidence: **high**

## 4. TurboQuant vs PQ: Key Theoretical Advantages

**Claim** | TurboQuant is "data-oblivious" — it requires no per-dataset training, no calibration set, and no codebooks to persist. The codebook is derived once from the standard normal distribution and is universal. By contrast, PQ requires a learned codebook trained on representative data and shipped alongside the index. | Source: Qdrant TurboQuant blog (May 2026); TurboQuant paper [arXiv:2504.19874] | Confidence: **high**

**Claim** | TurboQuant achieves near-optimal distortion rates (within a small constant factor ≈ 2.7x of information-theoretic lower bounds) across all bit-widths and dimensions. This is a formal theoretical guarantee that PQ lacks. | Source: TurboQuant paper abstract [arXiv:2504.19874] | Confidence: **high**

**Claim** | TurboQuant's three-step recipe: (1) apply random orthogonal rotation (Hadamard), which redistributes per-coordinate variance evenly so each coordinate looks roughly Gaussian; (2) quantize each coordinate independently with a fixed Lloyd-Max codebook for N(0,1); (3) score quantized vectors by reconstructing the dot product directly from codebook indices — no rotation inversion needed. | Source: Qdrant TurboQuant blog; Google Research blog (March 2026) | Confidence: **high**

**Claim** | TurboQuant's indexing time is "virtually zero" — no training pass is needed. PQ requires a k-means training step that can be slow for large nbits values and must be repeated if the dataset changes significantly. | Source: TurboQuant paper; Qdrant TurboQuant blog | Confidence: **high**

**Claim** | PolarQuant (a component of TurboQuant) converts vectors to polar coordinates, exploiting the fact that after rotation, the angle distribution is concentrated and known. This eliminates the memory overhead of per-block quantization constants that plague traditional PQ — TurboQuant avoids the 1-2 extra bits per number that other methods must spend on overhead. | Source: Google Research blog (March 2026); PolarQuant paper [arXiv:2502.02617] | Confidence: **high**

**Claim** | At 4-bit compression (8x), TurboQuant is competitive with SQ (4x) — meaning it matches SQ recall at half the storage, and significantly outperforms what PQ achieves at the same storage budget. | Source: Qdrant benchmark table across 10 datasets | Confidence: **high**

## 5. Google ScaNN Approach and Relationship to TurboQuant

**Claim** | Google ScaNN (Scalable Nearest Neighbors) introduced Anisotropic Vector Quantization (AVQ), which optimizes a family of anisotropic loss functions that penalize the parallel component of a residual more than the orthogonal component. This is based on the observation that for inner product search, the highest-scoring database points matter most. | Source: Guo et al., "Accelerating Large-Scale Inference with Anisotropic Vector Quantization" [arXiv:1908.10396] (2019) | Confidence: **high**

**Claim** | ScaNN uses random rotation (similar to TurboQuant) before quantization to distribute variance, combined with learned anisotropic quantizers. It achieves state-of-the-art results on ann-benchmarks. | Source: [arXiv:1908.10396] | Confidence: **high**

**Claim** | TurboQuant generalizes the ScaNN insight: instead of learning anisotropic quantizers per dataset, TurboQuant proves that a random Hadamard rotation + universal Lloyd-Max codebook is near-optimal (within 2.7x of the theoretical lower bound) for ANY vector distribution. This makes ScaNN's data-dependent approach theoretically unnecessary for the quantization step itself. | Source: TurboQuant paper [arXiv:2504.19874]; comparison to ScaNN in Google Research blog | Confidence: **medium** (theoretical relationship is clear; practical ScaNN may still win on specific distributions)

**Claim** | DB-Strike's INT8 quantization is described as "Google-QAT-style" and explicitly references ScaNN/AQT research in its module documentation: "Recall drop is ~1-2% at 384-1536 dim per Google's ScaNN / AQT research." | Source: DB-Strike `vector.rs` line 1 | Confidence: **high**

**Claim** | The key evolution: ScaNN (2019) → learned anisotropic codebooks → RaBitQ (2024) → rotation + 1-bit error correction → TurboQuant (2025/ICLR 2026) → rotation + universal Lloyd-Max + QJL residual, with formal optimality proofs. | Source: Paper timeline [arXiv:1908.10396], [arXiv:2405.12497], [arXiv:2504.19874] | Confidence: **high**

## 6. Residual Quantization Techniques and Evolution

**Claim** | Residual quantization (RQ) is a hierarchical approach: quantize the input vector, compute the residual (error), then quantize the residual, and repeat. Each level captures what the previous level missed. This is distinct from PQ which quantizes non-overlapping subspaces. | Source: Standard vector quantization literature; Jégou et al. (2010); TurboQuant paper discusses MSE quantizer + QJL residual as a 2-level residual scheme | Confidence: **high**

**Claim** | TurboQuant implements a form of residual quantization: the first stage uses PolarQuant (MSE-optimal scalar quantization per coordinate) to capture the bulk of the signal, then the second stage applies a 1-bit QJL transform on the residual to eliminate bias in inner product estimation. This two-stage approach achieves unbiased inner-product quantization. | Source: TurboQuant paper [arXiv:2504.19874], Google Research blog | Confidence: **high**

**Claim** | Google ScaNN's residual quantization (RQ) is one of the most effective ANN methods — it hierarchically quantizes residuals across multiple codebooks. The key insight is that the first codebook captures most of the vector, and subsequent codebooks capture the error, with each level using learned codebooks. | Source: ScaNN paper [arXiv:1908.10396]; ann-benchmarks results | Confidence: **high**

**Claim** | The evolution of residual quantization for ANN: (1) Basic PQ (2010) — independent subspaces, no residual; (2) Optimized PQ (OPQ) — learned rotation + PQ; (3) ScaNN RQ (2019) — hierarchical residual quantization with learned codebooks; (4) RaBitQ (2024) — rotation + 1-bit with theoretical error bounds; (5) TurboQuant (2025) — data-oblivious rotation + universal codebook + QJL residual, provably near-optimal. | Source: Paper timeline across [arXiv:1908.10396], [arXiv:2405.12497], [arXiv:2504.19874] | Confidence: **medium** (evolution narrative synthesized; individual papers are high-confidence)

**Claim** | Qdrant's TurboQuant implementation uses the MSE variant (not PROD) because it supports symmetric scoring (needed for HNSW graph construction, relevance feedback) and is more bit-efficient — PROD spends bits on a QJL correction that Qdrant instead handles via length renormalization (4 bytes per vector from RaBitQ). | Source: Qdrant TurboQuant blog (May 2026) | Confidence: **high**

## 7. The "Exact Rerank" Pattern

**Claim** | DB-Strike uses the two-stage pattern: "quantized traversal + f32 rerank" — navigate the HNSW graph using cheap INT8/TurboQuant distances, collect ef candidates, then rerank those candidates with exact f32 dot products. This is the same pattern Qdrant and Milvus use. | Source: DB-Strike `vector.rs` lines 634-636, 4073 | Confidence: **high**

**Claim** | The exact f32 rerank pattern works because HNSW's graph traversal only needs approximate distance ordering to follow the correct path — the quantized distance is sufficient for navigation. The final candidate set (typically ef=100-200 vectors) is small enough that exact f32 comparison is cheap. The f32 rerank "recovers the recall the coarse codes lose." | Source: DB-Strike `vector.rs` lines 634-636 | Confidence: **high**

**Claim** | DB-Strike keeps the raw f32 vectors in the MVCC substrate under `vec:<id>` — only the in-memory HNSW uses quantized vectors. `get_vector(id)` returns exact original bytes, so non-search consumers (exact rerank, export) are unaffected. | Source: DB-Strike `vector.rs` lines 20-24 | Confidence: **high**

**Claim** | DB-Strike also supports an NVMe cold tier where f32 rerank originals are spilled to disk, served by OS page cache. This allows holding 10M+ 768-d vectors in RAM while still having f32 rerank available from NVMe. | Source: DB-Strike `vector.rs` lines 187, 1565, 3391 | Confidence: **high**

**Claim** | Qdrant implements the same pattern: quantized vectors for fast HNSW traversal, with an optional `always_ram` flag for quantized vectors and original f32 vectors stored for exact reranking/rescoring. The `oversampling` parameter controls how many candidates to collect before reranking. | Source: Qdrant quantization docs (Binary Quantization section: "we recommend using binary quantization only with rescoring enabled") | Confidence: **high**

**Claim** | The "quantized + rerank" pattern is what allows DB-Strike to hold 10M+ 768-d vectors at Qdrant-class recall while using ~16-32x less RAM for the graph traversal portion. The f32 rerank on ~200 candidates is negligible compared to the savings on millions of vectors. | Source: DB-Strike `vector.rs` lines 3778, 634-636 | Confidence: **high**

**Claim** | In DB-Strike, the search path uses a `use_rerank` flag that switches between: (a) quantized-only scoring (fast, lower recall), and (b) quantized navigation + f32 rerank (slower per-query, near-perfect recall). The query is prepared differently for each path — in rerank mode, both a quantized and f32 version of the query are maintained. | Source: DB-Strike `vector.rs` lines 2196-2201 | Confidence: **high**

## 8. New Quantization Papers from 2025-2026

**Claim** | TurboQuant [arXiv:2504.19874, submitted April 2025, ICLR 2026] — the most significant recent paper. Proves near-optimal distortion rates for data-oblivious vector quantization. Achieves 3.5 bits/channel for absolute quality neutrality in KV cache, outperforms PQ in recall with virtually zero indexing time for ANN search. | Source: [arXiv:2504.19874] | Confidence: **high**

**Claim** | PolarQuant [arXiv:2502.02617, AISTATS 2026] — converts vectors to polar coordinates recursively, eliminating the per-block quantization constant overhead. As a component of TurboQuant, it provides the MSE-optimal first stage. | Source: [arXiv:2502.02617]; Google Research blog (March 2026) | Confidence: **high**

**Claim** | QJL (Quantized Johnson-Lindenstrauss) [arXiv:2406.03482, AAAI 2025] — reduces each coordinate to a single sign bit with zero memory overhead. Uses a special estimator that balances high-precision query with low-precision data for unbiased attention score computation. Serves as TurboQuant's residual correction stage. | Source: [arXiv:2406.03482]; Google Research blog (March 2026) | Confidence: **high**

**Claim** | RaBitQ [arXiv:2405.12497, SIGMOD 2024] — quantizes D-dimensional vectors into D-bit strings with a provable theoretical error bound. Outperforms PQ and variants in accuracy-efficiency trade-off. Qdrant borrows its length renormalization and bit-plane scoring ideas for its TurboQuant implementation. | Source: [arXiv:2405.12497]; Qdrant TurboQuant blog | Confidence: **high**

**Claim** | Google Research blog (March 24, 2026) announces TurboQuant as enabling "massive compression for large language models and vector search engines," with 4-bit TurboQuant achieving up to 8x performance increase over 32-bit unquantized keys on H100 GPUs. | Source: research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/ | Confidence: **high**

**Claim** | As of July 2026, no published paper improves on TurboQuant's theoretical bounds. The paper proves TurboQuant matches information-theoretic lower bounds within a ≈2.7x constant factor, which is near the fundamental limit of what any vector quantizer can achieve. | Source: TurboQuant paper [arXiv:2504.19874]; literature search as of July 2026 | Confidence: **medium** (no counter-paper found, but the field moves fast)

## 9. The Role of Hadamard Rotation in Quantization

**Claim** | The Hadamard transform is an orthogonal, symmetric, involutive linear operation using only {+1, -1} entries (no multiplications — only sign flips). It can be computed in O(D log D) via the fast Walsh-Hadamard transform. | Source: Wikipedia "Hadamard transform"; Wikipedia "Fast Walsh-Hadamard transform" | Confidence: **high**

**Claim** | Hadamard rotation spreads variance uniformly across coordinates. After applying a random Hadamard rotation to any input vector, each coordinate of the result has roughly the same variance — regardless of the original distribution. This is the Johnson-Lindenstrauss lemma in action: random projections preserve pairwise distances. | Source: TurboQuant paper [arXiv:2504.19874]; Johnson-Lindenstrauss lemma theory | Confidence: **high**

**Claim** | The key insight: after Hadamard rotation, the per-coordinate distribution becomes approximately N(0, σ²) regardless of the input distribution (assuming sufficient dimensionality). This means a SINGLE universal Lloyd-Max codebook (fitted once for the standard normal) works for ALL datasets and ALL dimensionalities — no training needed. | Source: Qdrant TurboQuant blog (May 2026); TurboQuant paper | Confidence: **high**

**Claim** | The Hadamard transform is a special case of the Johnson-Lindenstrauss transform — it's a structured (fast) random projection that achieves the same distance-preserving properties as a fully random Gaussian matrix, but with O(D log D) computation instead of O(D²). | Source: Wikipedia; TurboQuant paper; QJL paper [arXiv:2406.03482] | Confidence: **high**

**Claim** | Qdrant implements Hadamard rotation via a reversible LCG (Linear Congruential Generator) + Fisher-Yates shuffle to generate a random permutation, then applies the Hadamard transform. The rotation is deterministic given a seed, so the same rotation applies to both stored vectors and queries. | Source: Qdrant TurboQuant blog, "Further Reading" section referencing Ivan Pleshkov's engineering deep-dive | Confidence: **high**

**Claim** | The Hadamard transform is also used in locality-sensitive hashing (LSH) to obtain pseudo-random matrix rotations, in JPEG XR and MPEG-4 AVC video compression, and in quantum computing (the Hadamard gate creates uniform superposition). | Source: Wikipedia "Hadamard transform" - Other applications section | Confidence: **high**

**Claim** | Without Hadamard rotation, binary/scalar quantization fails on anisotropic data where a few directions concentrate most variance. The rotation step ensures that high-variance directions get spread across all coordinates, making the fixed N(0,1) codebook applicable. | Source: Qdrant TurboQuant blog, "Per-Coordinate Calibration" section | Confidence: **high**

## 10. Practical Guidance: When to Use Which Quantization Mode

**Claim** | Use **INT8 Scalar Quantization** when: you need the best accuracy with 4x compression, or when using Manhattan (L1) distance (which is incompatible with Hadamard rotation). Default choice for most workloads. | Source: Qdrant quantization docs; DB-Strike `QuantMode::Int8` as default | Confidence: **high**

**Claim** | Use **TurboQuant 4-bit** when: you want comparable recall to SQ at half the memory (8x vs 4x). This is the "easiest upgrade call on the ladder" from SQ. Works with Cosine, Dot, and L2 metrics. | Source: Qdrant TurboQuant blog (May 2026) | Confidence: **high**

**Claim** | Use **TurboQuant 2-bit** when: you need 16x compression and can tolerate some recall loss. It consistently beats BQ 2-bit by 9-24 pp at the same storage. | Source: Qdrant TurboQuant blog benchmarks | Confidence: **high**

**Claim** | Use **TurboQuant 1.5-bit** when: 32x is too aggressive but 16x leaves storage on the table (~21x compression). | Source: Qdrant TurboQuant blog | Confidence: **high**

**Claim** | Use **TurboQuant 1-bit** when: you need maximum compression (32x) with better recall than BQ 1-bit. Beats vanilla BQ by 9-21 pp; beats asymmetric BQ by 0.1-10 pp. | Source: Qdrant TurboQuant blog benchmarks | Confidence: **high**

**Claim** | Use **Binary Quantization** when: you need the fastest possible search (Hamming distance via popcount), your vectors are high-dimensional (≥768d) with centered distributions, and you can tolerate lower recall. Also use BQ if TurboQuant shows a noticeable throughput drop on your specific workload. | Source: Qdrant quantization docs; Qdrant TurboQuant blog | Confidence: **high**

**Claim** | Use **Product Quantization** when: memory footprint is the absolute top priority (up to 64x compression) and accuracy/speed are not critical. Requires training on representative data. | Source: Qdrant quantization docs | Confidence: **high**

**Claim** | Always pair quantized traversal with **exact f32 rerank** on the candidate set (ef=100-200 vectors). This recovers recall with negligible overhead — the rerank cost is trivial compared to the memory savings on millions of vectors. | Source: DB-Strike `vector.rs` lines 634-636; Qdrant docs ("we recommend using binary quantization only with rescoring enabled") | Confidence: **high**

**Claim** | For L1 (Manhattan) distance: stay on SQ. Hadamard rotation preserves L2 norm but not L1 norm — there is no clean way to make TurboQuant work with L1 without inverting the rotation per score, which defeats the speedup. | Source: Qdrant TurboQuant blog | Confidence: **high**

**Claim** | Decision matrix summary from Qdrant:
  - 4x compression → SQ
  - 8x compression → TQ 4-bit (or SQ if L1 needed)
  - 16x compression → TQ 2-bit (better recall) or BQ 2-bit (faster)
  - 21x compression → TQ 1.5-bit
  - 32x compression → TQ 1-bit (better recall) or BQ 1-bit (faster)
  - Up to 64x → PQ (only if memory is paramount)

  | Source: Qdrant quantization docs "How to Choose" section | Confidence: **high**

## Summary of Key Relationships

```
ScaNN (2019)          Learned anisotropic quantizers + random rotation
    ↓
RaBitQ (2024)         Rotation + 1-bit + theoretical error bounds
    ↓
TurboQuant (2025)     Rotation + universal Lloyd-Max + QJL residual
                       Provably near-optimal (≈2.7x of lower bound)
    ↓
Qdrant 1.18 (2026)    TurboQuant + RaBitQ renormalization + anisotropy
                       compensation + SIMD kernels (AVX-VNNI/NEON)
    ↓
DB-Strike (2026)      INT8/Turbo*/Binary/PQ + f32 rerank pattern
                       Same architecture, different default (INT8)
```

**Core insight**: The field is moving from data-dependent quantization (PQ, ScaNN) toward data-oblivious quantization (TurboQuant, RaBitQ) with formal guarantees. The practical implication: TurboQuant's zero-training-time + higher recall at equivalent compression makes it the superior choice for most production workloads, while INT8 remains the safe default for maximum accuracy.
