Introduction

Every existing system treats its "modern" capability as a bolt-on owned by someone else, on a different license and release cadence. StrikeDB's design philosophy is the opposite: it's a general-purpose data engine where relational, KV, vector, time-series, and pub/sub are all views over one storage substrate. AI/RAG is one first-class citizen among several, not the organizing principle.

Combined-Apple approach: take each category leader's advantage (Redis' speed, Postgres' relational rigor, Milvus' scale, Mem0's memory, SpacetimeDB's in-DB logic) and fulfill the database gaps with novel in-house approaches — one license, one consistency model.

The engine is pure Rust, zero external crates. The storage layer, HNSW vector index, agent memory, RAG pipeline, MITM cache debugger, reducers, RESP wire, reactive CDC, and HLC/CRDT consensus primitives are all implemented from scratch in the standard library.

Install & Run

# build the release binary (no external crates)
cargo build --release

# serve the RESP wire on 127.0.0.1:6380
DBSTRIKE_WAL=./dbstrike.wal ./target/release/dbstrike 127.0.0.1:6380

Talk to it with any Redis client, plain nc, or the bundled harness:

redis-cli -p 6380 PING            # -> PONG
redis-cli -p 6380 SET user:1 ada
redis-cli -p 6380 VADD 1 1.0 0.0 0.0
redis-cli -p 6380 VSEARCH 5 1.0 0.0 0.0

# full production test + benchmark suite (self-spawns the binary)
python3 tests/test_dbstrike.py
The suite runs 8 groups — correctness, AI/vectors, time-series, reducers, CDC, latency, throughput, and a real-time agent-memory scenario — and reports p50/p90/p99 latency and ops/sec. Exit code 0 = all green.

Unified substrate

At the core is an MVCC + WAL engine. Every key maps to a version chain ordered by commit timestamp. Readers take a snapshot and see the newest version ≤ snapshot; writers buffer in a transaction and commit atomically — the WAL record is fsynced first, then the in-memory version chains update. This gives snapshot isolation and crash recovery by replay.

Tables, KV, vectors, time-series, and the CDC log are key conventions over this one substrate. There is no second engine to drift from, no dual-write, no separate consistency model.

Transactions use optimistic concurrency control: a commit aborts (with a clean rollback) if any key it read was modified after its snapshot. See crates/storage.

Views: KV / Table / Vector / Time-series

All four are thin schemas over the substrate:

  • KV — opaque byte values, TTL-capable, prefix scans.
  • Tables — rows addressed by string PK, columns as a small map. The router joins these with vectors.
  • Vector (HNSW) — cosine-distance ANN index rebuilt from durable vec: keys on open. Filtered search (post-filter over a widened candidate set) supports the planner's selectivity decisions.
  • Time-series — append-only (series, ts, val), inclusive range queries.

Filtered ANN planner. pgvector's specific gap is that the planner doesn't treat vector distance as a cost-aware operator, so filtered similarity search is bolted on. StrikeDB's router estimates predicate selectivity and chooses PreFilter (filter-then-scan, for very selective predicates ≤5%) vs PostFilter (index-then-filter). One query does "10 most similar tickets, only paying customers, still open" under one plan and one snapshot.

Fuel-metered reducers

Following SpacetimeDB's "logic in the database" idea — but fixing its reducer-stall problem: every reducer ran in one global critical section, so a single bad reducer degraded the whole DB. Three in-house fixes:

  1. fixBulkhead by shard — a reducer locks only its key-range, not the world.
  2. fixFuel metering — every instruction is charged against a per-reducer budget via a tiny stack VM; overrun aborts and rolls back cleanly.
  3. fixCircuit breaker — a reducer erroring above a threshold is auto-quarantined until manually re-enabled.
# a fuel-metered counter reducer (invoked over a shard)
REDUCE hit shardA kv:hits 5    # -> 5
REDUCE hit shardA kv:hits 5    # -> 10
REDUCE hit shardA kv:hits 3    # -> 13
Under 16-way contention the reducer loses zero updates (the bulkhead serializes the shard, not the engine). p99 = 38.8µs.

Reactive sync & CDC

The engine's commit hook feeds a reactive hub that routes committed mutations to topic subscribers by key prefix, and keeps a durable change-data-capture log. Subscribers see committed changes after they're durable — decoupled from the write path (they may lag the strictest snapshot, the deliberate availability trade from the architecture).

AI agent memory

Four memory structures on the same substrate, with provenance / lineage as a first-class primitive — the non-malleable-authority hardening 2026 agent-memory research (MemLineage, poisoning defenses) demands and Mem0 / Zep / Letta don't ship.

  • WMWorking memory (STM) — hot per-agent context, TTL-cleared, Redis speed, same rows the durable engine sees.
  • LTMLong-term memory — durable semantic store, pushed into the shared HNSW for one-hop recall. Lineage-attached (source, created_ts, salience, derivation chain).
  • EPEpisodic — append-only event log, queryable by agent + kind.
  • KWKeyword index — BM25-ish inverted index for exact-term recall that pure-vector memory misses.

Recall is blended semantic + keyword, ranked by a salience-weighted score so important memories surface. This is what's built to beat Mem0 (26% accuracy lift on LoCoMo) and Zep/Letta.

# remember (source + salience + embedding)
MEM.REMEMBER "user prefers Rust for speed" user 0.9 1.0 0.2 0.0
# recall blended by similarity + keyword + salience
MEM.RECALL 5 "rust speed preference" 1.0 0.2 0.0

RAG as a first-class query

Retrieval is hybrid: dense (HNSW ANN) + sparse (BM25 keyword), fused with Reciprocal Rank Fusion — the technique that consistently beats either signal alone — plus a lightweight lexical rerank. The RAG engine wraps agent memory and a MITM-guarded query cache.

RAG.INGEST "Rust ownership prevents data races" doc:rust 1.0 0.0 0.0
RAG.SEARCH 5 "nearest neighbor graph index" 1.0 0.0 0.0
# -> cached/fresh flag + (id, score, source, text) hits
Corpus cache is safe: every ingest bumps a monotonic corpus generation. A changed corpus can never serve a stale answer — the cache key includes the generation, and the MITM debugger records the source write.

MITM cache debugger

"Your vector index is a cache with no invalidation strategy." StrikeDB solves that at the engine level: a man-in-the-middle observer sits between any cache and the source-of-truth, stamping every entry with the authoritative engine version. On each read it classifies the outcome:

VerdictMeaning
HITcache value == engine value (fresh)
STALE_HITcache value != engine value — THE bug
MISSkey absent from cache
PHANTOMcached but engine has no value (missed invalidation)

Every event is time-stamped into a ring buffer you can dump, diff, and replay — provable per-key staleness with the exact version delta, no guessing.

CACHE.SRCSET user:1 alice        # authoritative write (bumps version)
CACHE.SET   user:1 alice        # populate cache
CACHE.GET   user:1               # -> HIT
CACHE.SRCSET user:1 alice-v2    # source updated, cache NOT invalidated
CACHE.GET   user:1               # -> STALE_HIT  (caught instantly)
CACHE.BUGS                      # list every bug trace

Example apps

Three runnable apps in demos/ use StrikeDB as a real backend over the RESP wire — no mocks. Run them with bash demos/run_demos.sh (builds if needed, starts the server, runs all three).

  • agent_memory_demo.py — an AI agent ("Atlas") with persistent working + long-term + graph + bi-temporal + procedural memory in one engine.
  • realtime_dashboard_demo.py — time-series ingest from 8 simulated devices, a live window read, pub/sub fan-out, and WAL-backed crash replay.
  • rag_demo.py — hybrid RAG (dense + sparse, RRF-fused) with the MITM cache debugger proving a stale corpus can never be served.
