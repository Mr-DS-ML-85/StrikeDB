Why StrikeDB exists

Every "modern" database treats its best feature as a bolt-on owned by someone else — different license, different release cadence, different place for drift to hide. StrikeDB is the opposite.

Relational tables, key-value, vectors, time-series, pub/sub, AI agent memory, and RAG are all views over one storage substrate. One engine. One consistency model. One license. Zero gaps.

StrikeDB is a single Rust binary — no bolt-ons, no external crates, no drift. It speaks Redis RESP, so any Redis client works unchanged. 40+ commands, case-insensitive, both array and inline forms.

Built in pure Rust with zero external crates. Every line — storage, HNSW, agent memory, RAG, MITM debugger, reducers, RESP wire, CDC, HLC, CRDTs — is hand-rolled in the standard library.

Quick Start

# build — zero deps, pure stdlib Rust
cargo build --release

# launch on the RESP wire
DBSTRIKE_WAL=./dbstrike.wal ./target/release/dbstrike 127.0.0.1:6380

Use any Redis client, nc, or the bundled harnesses:

redis-cli -p 6380 PING            # -> PONG
redis-cli -p 6380 SET user:1 ada
redis-cli -p 6380 VADD 1 1.0 0.0 0.0
redis-cli -p 6380 VADDNS face 2 1.0 0.0 0.0
redis-cli -p 6380 VSEARCH 5 1.0 0.0 0.0          # dense k-NN (ef=128)
redis-cli -p 6380 VSEARCHNS face 5 1.0 0.0 0.0   # namespace-scoped search
redis-cli -p 6380 VDEL 1                          # :1 — remove a vector (correct wrong agent memory)
redis-cli -p 6380 VSEARCH 5 F 3 1.0 0.0 0.0      # Module 4 filtered by category
redis-cli -p 6380 VSEARCH 5 H 0 1.0 1.0 0.0 0.0  # Module 5 hybrid dense+sparse
redis-cli -p 6380 VSEARCHA 5 1.0 0.0 0.0         # query-adaptive beam
redis-cli -p 6380 VCALIBRATE 384 50 10 ...       # fit learned beam model
redis-cli -p 6380 SUBSCRIBE trades &
redis-cli -p 6380 PUBLISH trades "hello"
redis-cli -p 6380 CHECKPOINT       # snapshot + WAL truncate

# native Rust bench — 27 sections, in-process
cargo run --release -p bench -- --wire-qps        # 1/100-client wire QPS (early exit)
cargo run --release -p bench -- --qdrant          # Module 6 face-off + parallel-ingest
cargo run --release -p bench -- --large           # 1M × 128-d
cargo run --release -p bench -- --xlarge          # 1M @ 384/768/1536-d

# wire-level pub/sub check
./target/release/dbstrike-bench --tcp 127.0.0.1:6380

# Python integration + fuzz + crash recovery
python3 tests/test_dbstrike.py
Env knobs: DBSTRIKE_WAL=<path> for WAL location (default: dbstrike.wal). DBSTRIKE_SYNC=0 skips the WAL entirely — writes apply directly to sharded maps, no fsync, no flusher round-trip. Reads still see the write (same process), but crash durability is dropped. Default is durable (fsync every batch). Great for sessions, presence, caches, and test rigs.

The RESP Wire

Speaks Redis RESP — any Redis client works unchanged. 40+ commands, case-insensitive, both array and inline forms. RESP2 + RESP3 compatible: HELLO 3 negotiates RESP3 (map handshake, _ nulls), so modern clients (redis-py ≥ 8, go-redis, jedis) connect out of the box alongside redis-cli and redis-benchmark.

One substrate to rule them all

At the core: an MVCC + WAL engine. Every key maps to a version chain ordered by commit timestamp. Readers snapshot, writers buffer and commit atomically — the WAL is fsynced first, then in-memory chains update.

Tables, KV, vectors, time-series, and CDC are key conventions over this one substrate. No second engine to drift from. No dual-write. No separate consistency model.

Optimistic concurrency control: a commit aborts cleanly if any read key was modified after its snapshot. 32 shards (FNV-1a), Redis-style {hash-tag} routing, group-commit flusher — one fsync per batch.

Views: KV / Table / Vector / Time-series

⚡

Opaque bytes, TTL, prefix scans. Pipelined SET/MSET coalescing — N writes, ONE fsync.

📊

Rows by string PK, column map, equality filters. Relational rigor on the same substrate.

🎯

INT8 quantization + f32 rerank. AVX2 SIMD. Filtered ANN, batched queries, ef tuning.

📈

Time-series

Append-only, hash-tagged shards. TSRANGE.LATEST: dashboard primitive at 52us p50.

{hash-tag} shard routing: ts:{cpu}:1234 hashes only on cpu, co-locating all points in ONE shard. TSRANGE skips 31 useless lock acquires.

Filtered ANN planner: cost-based PreFilter vs PostFilter — "10 most similar tickets, only paying customers, still open" under one plan.

The "speed of light" path

SpacetimeDB's pitch: logic inside the database eliminates the network hop. StrikeDB does the same — and fixes the one flaw that makes SpacetimeDB dangerous: the reducer-stall problem.

Measured: REDUCE p99 = 45.5us over RESP. Zero lost updates under 32-thread x 500-op contention (16,000/16,000 in 0.15s).

Fuel-metered reducers

Logic in the DB — but safe. Three in-house fixes for the SpacetimeDB stall:

  1. fix Bulkhead by shard — a reducer locks only its key-range, not the world.
  2. fix Fuel metering — every instruction charged against a budget. Overrun = clean rollback.
  3. fix Circuit breaker — erroring reducers auto-quarantined until re-enabled.
# fuel-metered counter reducer
REDUCE hit shardA kv:hits 5    # -> 5
REDUCE hit shardA kv:hits 5    # -> 10
REDUCE hit shardA kv:hits 3    # -> 13

Reactive sync & SUBSCRIBE/PUBLISH

Commit hook feeds a reactive hub — mutations route to subscribers by key prefix, durable CDC log underneath.

Redis-compatible pub/sub over the wire. PUBLISH is a durable write on chan:<name> — every subscriber receives via the same MVCC+WAL substrate.

# terminal A
redis-cli -p 6380 SUBSCRIBE trades

# terminal B
redis-cli -p 6380 PUBLISH trades "AAPL 42"
# -> 1) "message"  2) "trades"  3) "AAPL 42"
Round-trip PUBLISH->SUBSCRIBE: p50 = 31us, p99 = 120us over the wire.

AI agent memory

Every category leader's core primitive, on one substrate, in one process. Seven memory structures with provenance/lineage as a first-class primitive.

WM

Working Memory

Hot per-agent context, TTL-cleared. Redis speed on the durable engine.

LTM

Long-Term Memory

Durable semantic store in HNSW. Lineage-attached: source, salience, derivation chain.

EP

Episodic

Append-only event log. Queryable by agent + kind. The event timeline.

KW

Keyword Index

BM25 inverted index. Exact-term recall that pure-vector memory misses.

GRAPH

Graph Memory

Typed edges, forward + reverse index. MEM.LINK / NEIGH / TRAV for BFS traversal.

BITEMP

Bi-temporal Facts

valid_from / valid_to on LTM. RECALL.AS_OF: "what did we know at time T?"

PROC

Procedural Memory

Per-agent workflows and rules. Stored by name, retrieved on demand.

Blended recall: semantic ANN + BM25 keyword, ranked by salience-weighted score via in-memory cache. Zero substrate reads during scoring.

# remember
MEM.REMEMBER "user prefers Rust for speed" user 0.9 1.0 0.2 0.0

# blended recall
MEM.RECALL 5 "rust speed preference" 1.0 0.2 0.0

# graph edges
MEM.LINK alice works_at acme 1.0
MEM.TRAV alice 3

# bi-temporal
MEM.REMEMBER.T "CEO of Acme" user 0.8 3000 0 1.0 0.2 0.0
MEM.RECALL.AS_OF 5 "CEO" 5000 1.0 0.2 0.0

# working memory (TTL-cleared per-agent context)
MEM.WM_SET alice session_ctx "midnight launch plan" 60000
MEM.WM_GET alice session_ctx
MEM.WM_DELETE alice session_ctx

# episodic — append-only event log, queryable by agent + kind
MEM.EPISODE alice click '{"page":"/pricing"}'
MEM.EPISODES alice 50
MEM.EPISODE_FORGET alice <seq>

RAG as a first-class query

Hybrid retrieval: dense (HNSW) + sparse (BM25), fused with Reciprocal Rank Fusion — the technique that consistently beats either signal alone — plus lexical rerank.

RAG.INGEST "Rust ownership prevents data races" doc:rust 1.0 0.0 0.0
RAG.SEARCH 5 "nearest neighbor graph index" 1.0 0.0 0.0
# -> cached/fresh flag + (id, score, source, text) hits
Corpus cache is safe: every ingest bumps a monotonic generation. Stale answers are structurally impossible.

MITM cache debugger

"Your vector index is a cache with no invalidation strategy." StrikeDB solves that: a man-in-the-middle stamps every cache entry with the authoritative engine version.

Reproduce these numbers

Build the release binary, raise the per-process fd limit, then run with -c 100 (the sweet spot — -c 50 under-saturates the group-commit flusher and drops to ~600k/s; -c 200+ contends on it). Numbers vary run-to-run; the table above is the typical envelope.

cargo build --release
ulimit -n 100000

pkill -9 dbstrike 2>/dev/null; sleep 0.3
rm -f /tmp/dbstrike_p256.wal /tmp/dbstrike_p256.wal.snap
DBSTRIKE_WAL=/tmp/dbstrike_p256.wal ./target/release/dbstrike 127.0.0.1:6433 >/dev/null 2>&1 &
SVR=$!; sleep 0.3

echo "== DURABLE @ -P64 ==";  redis-benchmark -h 127.0.0.1 -p 6433 -P 64  -c 100 -n 200000 -t set,get 2>&1 | grep "throughput summary"
echo "== DURABLE @ -P256 =="; redis-benchmark -h 127.0.0.1 -p 6433 -P 256 -c 100 -n 400000 -t set,get 2>&1 | grep "throughput summary"
echo "== DURABLE @ -P1024 ==";redis-benchmark -h 127.0.0.1 -p 6433 -P 1024 -c 100 -n 1000000 -t set,get 2>&1 | grep "throughput summary"

kill -9 $SVR; sleep 0.3
echo "== NON-DURABLE (DBSTRIKE_SYNC=0) @ -P256 =="
rm -f /tmp/dbstrike_p256.wal
DBSTRIKE_WAL=/tmp/dbstrike_p256.wal DBSTRIKE_SYNC=0 ./target/release/dbstrike 127.0.0.1:6434 >/dev/null 2>&1 &
SVR=$!; sleep 0.3
redis-benchmark -h 127.0.0.1 -p 6434 -P 256 -c 100 -n 400000 -t set,get 2>&1 | grep "throughput summary"
kill -9 $SVR; wait 2>/dev/null; true

Typical envelope on the reference box: SET 5.88M / 12.1M / ~17M and GET 5.88M / 13.3M / 16.4M ops/s at -P 64 / 256 / 1024. Redis 8.0.5 (same box) lands at 2.94M SET (in-mem) / 2.30M (AOF) and 4.17M GET — so StrikeDB is ~3-6x faster on the pipelined path.

GPU — APGC build + batched search (experimental)

100k × 384-d real embeddings on one RTX 4060 (8 GB, 24 SMs) + Ryzen 7 7700 (16 threads). Kernels compiled at runtime via NVRTC — no cuBLAS, no BLAS, no build-time CUDA dependency. Reproduce in ~25s: dbstrike-bench --gpu-bench <vectors.fbin>.

The GPU wins on build (~3×). It does not beat a saturated 16-core CPU on search at this scale. A graph query is one CUDA block, so a lone query leaves 23 of 24 SMs idle — and 16 client threads is still only 16 blocks, which is why raising concurrency never rescues it. Batched GPU search reaches 22,116 QPS — 7.73× a single CPU core, but 0.79× the 27,894 QPS sixteen CPU threads deliver. An earlier revision of this page claimed 12.4× by comparing an unequal search beam against a single-threaded baseline; that is retracted. Forced onto the device with DBSTRIKE_GPU_SINGLE=1, a single query manages 0.61× the CPU — so search_ef routes by query shape and search_many gets the device, rather than making you know this and pick a mode. Two candidate explanations were tested and ruled out: the query coalescer (GPU_COALESCE=0 moves single-query throughput ~1%) and a shared-memory cliff (7–12 KB used against the 48 KB limit, so no silent fallback to brute force).

Caveats. The 1-thread and 16-thread columns are CPU search in every row, so they measure graph quality rather than hardware — Turbo wins them because the APGC graph is cheaper to walk. Only the batch column is GPU search. VUGVA's VRAM→DRAM→NVMe tier is wired and hardware-tested (a corpus 1.5× the DRAM budget spills to NVMe and promotes back byte-exact; look-ahead prefetch overlaps transport at 3.2×), but a 36 MB corpus never stresses it, so the larger-than-VRAM case is not yet benchmarked end to end. 1M×384-d and 1M×768-d GPU figures are not yet measured. Wire ingest still uses the serial append path.

make prove-it — the public evidence engine

One command, RESP-only, stdlib-only, ~11 seconds. Six phases, 31 checks — crash durability under randomized SIGKILL with mixed workloads, bulk-load atomicity (0 or full namespace, never partial), 8-client INCRBY consistency, mixed-workload invariant fuzz, per-subsystem durability, and the FLUSHALL backup-restore round trip. Exit 0 only if every proof held.

make prove-it        # or: python3 scripts/prove_it.py

It already caught two real bugs unit tests missed: concurrent INCRBY lost updates (OCC validation raced the group-commit queue) and a restart-time collision between user vectors and LTM embeddings sharing one namespace. Both fixed; the proofs run against the fixed build.
